1. Executive summary

70 / 100 overall QA score (round 1: 58)

The fix round worked. Of the 26 round-1 findings, 21 are fixed and 5 are partly fixed. None are unfixed or regressed. The outbox was rewritten and now behaves as promised: it keeps a write until the server accepts it, retries 5xx and unreachable servers forever, pauses on 401 instead of wiping, and lifts queued edits over the create they follow. A probe that replays real OutboxQueue writes against the in-memory API confirmed this. Bangla digits parse, bill payments and timer stops replay safely, and rollover and foreign-currency budgets are right. The test suite went from 185 to 568 passing tests, and the assertions are meaningful.

The new code brought new failure modes, and two are serious. QA-201: any signed-in user can crash the whole API in a restart loop by setting an invalid time zone. A plain PATCH /settings or the assistant's update_settings is enough, because the hourly job runner lets the error escape and Bun exits. A user database that fails migration 0004 does the same. QA-202: refreshing the token revokes the old one at once, so a request still carrying it gets a 401. The app then expires the session and discards the new token, which sends a daily user back to Google sign-in. Both were reproduced. Both are small fixes.

5.1 Server & scheduled jobs

QA-201 · One user's bad data takes the whole API down: an invalid time zone or a database that won't open crashes the job runner, and the server restart-loops

CriticalCategory: Server / availability / securityEffort: SReproduced

Where: apps/api/src/jobs/scheduler.ts:L36-L65 (loop), :L71-L85 (startJobs). packages/shared/src/schemas/settings.ts:L24 (timeZone: z.string()). apps/api/src/modules/ai/assistant/tools.ts:L517-L521 (update_settings forwards any fields, no Undo). apps/api/src/db/client.ts:L28-L33 plus drizzle/0004_constraints.sql.

What's wrong: In runHourlyJobs only job.run() is inside a try/catch. Opening the user's database (deps.users.lease, which also runs migrations), readSettings and localParts(now, timeZone) run inside a try { } finally { } with no catch, so any throw rejects the whole run. startJobs calls tick() from croner with no catch option, so croner rethrows. It also calls it from a setTimeout 10 s after start as void tick(). Nothing handles that rejection, and Bun exits with code 1. pm2 restarts the process, the catch-up runs 10 s later, and it crashes again.

There are two reproduced triggers:

  1. Invalid time zone. timeZone accepts any string, so PATCH /settings {"timeZone":"Dhaka"} answers 200. After that, this user's /today and /budgets/safe-to-spend answer 500, and runHourlyJobs rejects with RangeError: invalid time zone. Saying “set my time zone to Dhaka” to the assistant takes the same path. The app has no screen to change it back. The assistant can't fix it either, because it reads the time zone itself at the start of every turn.
  2. A database that won't open. Migration 0004 rebuilds tables with new CHECKs and aborts on any old row that breaks one, even a soft-deleted row. The round-1 transactionUpdateSchema allowed amountMinor: 0, so such rows can exist.
// scheduler.ts L38-L63 (trimmed)
for (const user of deps.users.list()) {
  await yieldToRequests();
  const lease = deps.users.lease(user);              // opens + migrates: may throw
  try {
    runAsUser({ user, data }, () => {
      const timeZone = readSettings(data.db).timeZone;
      const { hour } = localParts(now, timeZone);    // RangeError on "Dhaka"
      for (const job of JOBS) { try { job.run(...) } catch (error) { log(...) } }
    });
  } finally { lease.release({ closeIfOpened: true }); }   // no catch
}
// L80-L81
const job = new Cron("5 * * * *", { name: "per-user-jobs" }, tick);   // no catch option
const catchUp = setTimeout(() => void tick(), 10_000);
PATCH /settings {timeZone:'Dhaka'} -> 200
GET /today -> 500   GET /budgets/safe-to-spend -> 500   GET /tasks -> 200
other user GET /today -> 200
runHourlyJobs rejected: RangeError invalid time zone: Dhaka
unhandled.ts (same tick() shape, rejecting): error ... exit code 1

  openDatabase threw ... CHECK constraint failed: transactions_amount_check

Why it matters: One request from any signed-in account takes the service down for every user, and backups stop running because they live in the same loop. It is a denial-of-service hole as well as a crash. The affected user is also locked out of Today with no way to recover in the app.

Recommendation:

  1. Validate timeZone as a real IANA zone, for example z.string().refine(tz => { try { new Intl.DateTimeFormat("en", { timeZone: tz }); return true } catch { return false } }). Have readSettings fall back to the default when a stored value is invalid.
  2. In the job loop, wrap each user's whole body (lease included) in try/catch, then log and continue.
  3. Add .catch(log) to tick() and catch: true to the Cron.
  4. Add a process.on("unhandledRejection") logger as a backstop.
  5. Allow-list the keys update_settings may change, and give it an Undo.
  6. Before rebuilding tables in 0004, repair or log rows that would fail the new CHECKs.

5.2 Sessions

QA-202 · Refreshing the session signs the user out when another request still carries the old token

HighCategory: Auth / sessionEffort: S–MReproduced Unverified on a real network

Where: apps/api/src/modules/auth/routes.ts:L60-L65 (revoke in the same request). apps/mobile/src/lib/http.ts:L45-L54 (401 hook). apps/mobile/src/lib/auth.ts:L41-L56 (refresh on start), :L80-L91 (saveSession awaits 3 SecureStore writes before setting the token), :L150-L168 (refresh). apps/api/test/sessions.test.ts:L47-L49 asserts the instant revoke.

What's wrong: The phone refreshes on every cold start and foreground once the token is a day old. That is exactly when the Today query, the /sync/changes pull and the outbox all fire with the old token. The server revokes the old session inside /auth/refresh, so any of those requests that arrives afterwards gets 401 session_expired. The ky hook sees the header still matches the current token, because the new one isn't stored yet, and calls expireSession(), which clears the token. When the refresh reply arrives, tokenStore.get() === token is false and the new token is discarded. The old session is already revoked, so the user lands on the login screen. A lost refresh reply (timeout, network switch) ends the same way.

// refresh-race.ts: real http.ts hooks against the in-memory API, refresh reply delayed 300 ms
onUnauthorized -> expireSession(): token cleared
GET /today with the old token -> 401
refresh reply 200; tokenStore === old token? false -> DISCARDED
signed in afterwards: false
// server alone: refresh 200 | old token after refresh: 401 session_expired | new token: 200

Why it matters: Nothing is lost, because the queue is kept. But a daily user is sent back to Google sign-in whenever the race hits, and sign-in needs a network and Play services. Offline-first stops working until they sign in. It undoes much of the value of the QA-003 fix.

Recommendation:

  • Server: keep the replaced session valid for a short grace period (for example revoked_at = now + 2 min, or until the new jti is first used).
  • Client: while refreshing is pending, make beforeRequest await it, and ignore a 401 for the token being refreshed. Set the new token in memory before the SecureStore writes. Add a test with a 401 arriving mid-refresh.

5.3 Offline sync & local storage

QA-203 · An edit queued after a bulk move is silently discarded on replay

MediumCategory: Offline / last-write-winsEffort: MReproduced

Where: apps/api/src/lib/crud.ts:L170-L180. apps/api/src/modules/tasks/service.ts:L321-L372 (rescueOverdue), :L383-L430 (moveLowPriority). apps/mobile/src/lib/outbox-policy.ts:L95-L124.

What's wrong: The server keeps an edit only if the phone's edit time is not older than the row's updatedAt, and it stamps every write with the time it is processed. The round-1 fix (followCreatedRecords) lifts queued PATCHes to that stamp, but only when the reply contains the row with id and updatedAt, at the top level or one level down. rescue-overdue replies { moved: number, before: [...] } without updatedAt. move-low-priority replies with an array, which stampedRows doesn't walk. So if you go offline, tap “bring old tasks into today” and then rename one of them, the rename replays with an older time than the move. The server answers 200 and leaves the row unchanged.

NEW bulk-then-edit: rescue-overdue then rename offline, replay 2h later -> title: "Call bank"
  POST /tasks/rescue-overdue -> 200 | PATCH /tasks/01M48T... -> 200   (rename to "Call bank about card" lost)

Why it matters: This is silent loss of a user edit, the same class as round-1 QA-002 with a narrower trigger. The morning “bring old tasks into today” tap is a common first action.

Recommendation: Compare like with like. Store the client's last edit time separately from the server's updatedAt, and let a PATCH win over server-side bulk changes made before it was tapped. Failing that, have bulk endpoints return the stamped rows and teach stampedRows to walk arrays. Add an outbox-plus-API replay test.

QA-204 · A write the server keeps failing blocks every later write, and nothing on screen says so while the phone is online

MediumCategory: Offline / error visibilityEffort: MReproduced

Where: apps/mobile/src/lib/outbox-policy.ts:L68-L77. apps/mobile/src/lib/outbox-queue.ts:L160-L190. apps/mobile/src/components/ui/sync-status.tsx:L14 (if (online) return null). apps/api/src/middleware/error-handler.ts:L20-L33 (CHECK violations become 500). apps/mobile/src/lib/sync-changes.ts:L51.

What's wrong: The queue is strictly ordered and retries 5xx forever, which is the right default. But when one request fails deterministically with 5xx, the head entry retries every minute forever and every later write waits behind it. That happens on a server bug, or on a SQLite CHECK violation, which the error handler maps to 500 instead of 400. The /sync/changes pull also waits for an empty queue, so remote changes stop arriving too. The only pending indicator is hidden whenever the phone is online, so neither this case nor the round-1 scenario (Wi-Fi up, API down) is visible. There's no way to see, retry or discard a stuck write.

HEAD-OF-LINE (real OutboxQueue + API): PATCH /events {startsOn after endsOn} -> 500
  (CHECK constraint failed: events_range_check), then a ৳20 expense queued behind it:
  failed attempts 55 | queue size 2 | landed: [] | policy for 500: retry

Why it matters: The user believes their expenses are saved (“Saved on this phone. It'll sync…”). They may sit on one phone indefinitely while the server's numbers and backups drift.

Recommendation:

  • Map SQLITE_CONSTRAINT_CHECK and NOTNULL to 400 validation_error.
  • Show a pending chip whenever outbox.size > 0, online or not, and a “needs attention” state once the head entry has failed N times. Let the user retry or discard it there.
  • Consider parking an entry after N identical 5xx failures so later writes can go.

QA-205 · Expenses logged from the widget wait in a second, plain-text queue that the app doesn't count or protect

LowCategory: Widget / offlineEffort: S

Where: apps/mobile/src/features/widget/widget-task-handler.tsx:L17-L51. widget-cache.ts:L35-L68. use-widget-sync.tsx:L41-L49. lib/user-data.ts:L16-L33. features/settings/confirm-sign-out.ts.

What's wrong:

  • Offline widget taps go to tt.widget-pending in plain AsyncStorage (note, amount, account), outside the encrypted outbox.
  • They aren't counted in outbox.size, so the sign-out warning reports 0 unsynced changes, and clearUserData deletes them.
  • The hand-over is read → enqueue → writePendingLogs([]), so a widget tap landing in between is lost.
  • The widget cache (left-to-spend, next task title) is also plain text, unlike the “encrypted at rest” claim in secure-storage.ts.

Recommendation: Count pending widget logs in the sign-out check. Remove only the ids that were enqueued. Store the widget data through secureStorage, which the headless task can also read, or document the exception.

QA-206 · A stored value that fails to decrypt is deleted (including the offline queue), and encryption silently falls back to plain text

LowCategory: Storage / encryptionEffort: SUnverified

Where: apps/mobile/src/lib/encrypted-storage.ts:L36-L55. apps/mobile/src/lib/secure-storage.ts:L11-L23.

What's wrong: Any decrypt error removes the value. That is right for a key lost to a Keystore reset. But the same path runs if SecureStore.getItemAsync throws once: storageKey() rejects, decrypt throws, and the queued writes are deleted without a message. If the key can't be stored at all, every value is written in plain text with no log or flag.

Recommendation: Separate “wrong or missing key” (delete) from “key store unavailable” (keep, retry later). For the outbox, move undecryptable data aside and tell the user. Log the plain-text fallback.

QA-207 · On a cold start the saved queue can sit idle if it finishes loading before the session token

LowCategory: Offline / start-upEffort: SUnverified

Where: apps/mobile/src/app/_layout.tsx:L78-L81. lib/auth.ts:L41-L56. lib/outbox-queue.ts:L85-L101, L160-L165. lib/outbox.ts:L37.

What's wrong: load() kicks the queue once, and canSend() needs a token. loadToken() sets the token but never kicks the outbox; saveSession does, but that only runs on sign-in or refresh. Suppose the token is fresh (under 24 h, so no refresh) and the network and AppState don't change. If the outbox loads first, queued writes then wait until the next foreground or network change. It is timing-dependent, and the outbox read is usually the slower one.

Recommendation: Call outbox.kick() at the end of loadToken(), or subscribe the outbox to tokenStore.

5.6 Money, time & capture

QA-212 · Some tap times use the raw phone clock, so a phone running fast loses focus sessions and a slow one can lose offline edits

LowCategory: Time / clock skewEffort: SUnverified

Where: apps/mobile/src/features/focus/focus-screen.tsx:L44-L45, L92 (Date.now()). apps/mobile/src/lib/server-clock.ts:L6-L17 (offset kept only in memory). apps/api/src/modules/time-entries/service.ts:L19-L31 (rejects tap times more than 5 min in the future).

What's wrong: Focus start and stop use Date.now(), while every other write uses editTime(). The server-time offset is learned from responses and not persisted, so after an offline cold start editTime() is the raw phone clock too. Two consequences follow:

  • A phone 6 min fast has its focus start rejected with 400 (dropped, with a toast), and the stop then gets 404.
  • A phone a few minutes slow, edited offline after a cold start, loses last-write-wins against rows the server touched recently.

Recommendation: Use editTime() in focus. Persist the offset and restore it on start. On the server, clamp a slightly future tap time to now instead of rejecting it.

QA-213 · Foreign-currency spending still moves the taka safe-to-spend on screen, and Today's “Paid” sends foreign bills without a rate

LowCategory: Money / currencyEffort: S

Where: apps/mobile/src/lib/outbox.ts:L69-L80 (applyOptimistic). lib/optimistic-spend.ts:L34-L50. features/today/next-up.tsx:L36-L47.

What's wrong:

  • The server now leaves foreign accounts out (QA-009 fixed), but the optimistic update subtracts any expense. A $50 card expense takes ৳50 off “left today” until the next refetch, and offline that lasts until reconnect.
  • On Today, only foreign income opens the sheet. A USD bill whose account isn't in USD is posted straight to /pay, and the toast says “logged”. The server then answers 400 “Enter the USD → BDT rate”, and a second toast says it failed.

Recommendation: Skip the optimistic update when the account's currency isn't the default. Open the sheet for any item whose currency differs from its account's.

6. Strengths (keep these)

  • The outbox is now a real, testable component. The policy is pure (classifyFailure, retryDelay, followCreatedRecords). The queue owns its own storage, marks a possibly delivered first entry after a restart, and keeps writes queued before load in order. A 401 pauses it rather than wiping. Writes left by the old TanStack format are migrated.
  • Idempotency by design. Phone-made ids are used everywhere. Pay takes transactionId plus dueAt, stop takes an id, checkout takes a transactionId, and delete and restore return the row on repeat. Every one of these was re-run with the expected result.
  • Sessions are revocable and sliding. A jti sits in a sessions table, 401 codes say why, and the server has logout and account deletion. The client keeps the profile and queue for the same person and wipes only for a different account.
  • Bangla handled at the root. One toAsciiDigits runs before every parser, currency words are stripped, number words become labels (“৩ নম্বর”), and a Bangla title gets low confidence so the AI sees it. The quick-add table test covers dozens of cases.
  • The database enforces what zod enforces. CHECK constraints, foreign keys and self-reference checks were added, and the migration is tested on a populated database.
  • Assistant safety. The loop stops on client abort, the cost cap is checked before every model call, deletions need confirmation, model-chosen paths are checked with isPlainPath, and money writes in most forms are drafts.
  • Clean gates. Lint is clean, types are clean, and 568 tests pass with exact-value assertions and an injectable clock. CI runs all three on every push.
