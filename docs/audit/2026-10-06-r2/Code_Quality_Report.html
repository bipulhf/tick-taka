5.1 Reliability & data integrity

CQ-027 · An invalid time zone setting crashes the API in a restart loop

Critical · Reliability / security (denial of service) · Effort S · New · Reproduced
Where
packages/shared/src/schemas/settings.ts:24, apps/api/src/jobs/scheduler.ts:36-65, 72-86, apps/api/src/lib/user-time.ts:14, apps/api/src/modules/ai/assistant/tools.ts:517-522
What's wrong

timeZone is z.string(), so PATCH /settings {"timeZone":"Not/AZone"} is saved with a 200. After that, localParts() throws RangeError for this user. Every screen that reads their time (/today and others) returns 500.

The bigger problem is the job loop. In runHourlyJobs only job.run() sits inside a try/catch. deps.users.lease(user), readSettings() and localParts() are outside it, so one user's error rejects the whole run. Neither caller handles that rejection: the catch-up is setTimeout(() => void tick(), 10_000), and croner runs with catch: false and does not await _trigger(). Bun 1.3.11 exits on an unhandled rejection. pm2 restarts the process, the catch-up runs 10 s later, and it crashes again.

Sign-up is open to any Google account. The assistant can also hit this by accident: update_settings passes the model's fields straight to PATCH /settings, so "set my time zone to Dhaka" can save "Dhaka". A user DB that fails to open, for example a failed migration (CQ-032), takes the same path through lease().

Evidence

const lease = deps.users.lease(user);            // throws if the DB can't open
try {
  runAsUser({ user, data }, () => {
    const timeZone = readSettings(data.db).timeZone;
    const { hour } = localParts(now, timeZone);  // RangeError: invalid time zone
// scheduler.ts:80-81
const job = new Cron("5 * * * *", { name: "per-user-jobs" }, tick);
const catchUp = setTimeout(() => void tick(), 10_000);

One request from any account takes the API down for every user, and it stays down across restarts until someone fixes that user's settings row by hand in SQLite. The affected user's own app also breaks, because the phone computes dates with the same value.
Recommendation
Fix all three layers.

  await yieldToRequests();
  try { runJobsFor(deps, user, now); }                 // lease + runAsUser + release
  catch (error) { log("error", "user jobs failed", { user: userTag(...), ...errorFields(error) }); }
}
// and nothing can reject unseen
running ??= runHourlyJobs(deps).catch((e) => log("error", "job run failed", errorFields(e))).finally(...);
process.on("unhandledRejection", (e) => log("error", "unhandled rejection", errorFields(e)));
Add tests: PATCH with a bad zone returns 400, and runHourlyJobs still runs user B's jobs when user A's DB throws.

CQ-030 · CHECK violations return 500, and the outbox retries any 5xx forever at the head of the queue

Medium · Error handling / offline sync · Effort M · New · Reproduced (API side)
Where
apps/api/src/middleware/error-handler.ts:17-31, apps/api/src/modules/events/routes.ts:48-50, packages/shared/src/schemas/money.ts:264-273, apps/mobile/src/lib/outbox-policy.ts:73, apps/mobile/src/lib/outbox-queue.ts:160-199
What's wrong
Migration 0004 added 40 CHECKs, but the error mapper only knows FOREIGNKEY (400) and UNIQUE/PRIMARYKEY (409). A CHECK failure becomes internal_error 500. Partial PATCH schemas cannot check two fields against each other. eventUpdateSchema accepts endsOn alone, the route does not compare it with the stored startsOn, and the database refuses the row. On the phone, the outbox classifies every 5xx as retry, retries forever (capped at 60 s), and only ever sends entries[0]. A write the server always rejects with 5xx stays at the head, and every write queued after it waits behind it.
Evidence
$ bun probe-check.ts
POST /events {startsOn:"2026-10-10", endsOn:"2026-10-12"}  -> 201
PATCH /events/:id {endsOn:"2026-10-01"}  -> 500 {"error":{"code":"internal_error",...}}
// outbox-policy.ts:73
if (status >= 500 || status === 408 || status === 429) return "retry";
// outbox-queue.ts:164-165
while (this.entries.length > 0 && this.deps.canSend()) {
  const entry = this.entries[0]!;
Why it matters
The event sheet clamps endsOn (event-sheet.tsx:56), so this exact payload does not come from today's UI. The pattern is general, though. Any deterministic 5xx, whether an unmapped constraint or a bug in one service, quietly stops all syncing on that phone. The sync bar shows a count, but nothing lets the user see or drop the stuck write. Unsynced writes then pile up behind it, which the offline queue exists to prevent.
Recommendation
Map SQLITE_CONSTRAINT_CHECK and _NOTNULL to 400 invalid_value, so the outbox rejects the write and tells the user. Check cross-field ranges on PATCH against the stored row, as time-entries/service.ts:174-176 already does. In the outbox, mark an entry as stuck after about 8 failed 5xx attempts, keep sending the entries after it, and list stuck writes in Settings with Retry and Discard. Add a test with one poison entry followed by a good one.

CQ-028 · Encrypted storage deletes the queued writes when the key can't be read

Medium · Data integrity (client) · Effort S · New · Unverified on device (how often the trigger happens)
Where
apps/mobile/src/lib/encrypted-storage.ts:28-58, apps/mobile/src/lib/secure-storage.ts:11-35, apps/mobile/src/lib/outbox.ts:38-42, apps/mobile/src/lib/outbox-queue.ts:85-102, 236-245
What's wrong

getItem treats any error from cipher.decrypt as "the key is gone for good" and deletes the value. decrypt awaits storageKey(), which rejects whenever SecureStore.getItemAsync fails. That is the same Keystore read failure round 1 flagged in CQ-002, and here it can be temporary. A failed key read at start-up therefore deletes tt.outbox and the cached screens. Nobody is told.

Writes are protected the other way round: setItem falls back to plain text when the cipher fails, so writes are never lost but reads are. Even if getItem threw instead of deleting, OutboxQueue.load catches the error, marks itself loaded and persists an empty queue on the next write, which overwrites the unread data.

There is also a small race. Reading a plain value starts a re-seal (void cipher.encrypt(raw).then(setItem)) that is not ordered against later setItem calls, so it can write the older value over a newer one.

Evidence
// encrypted-storage.ts:33-45
if (!raw.startsWith(SEALED_PREFIX)) {
  void cipher.encrypt(raw).then((sealed) => base.setItem(key, SEALED_PREFIX + sealed)).catch(() => {});
  return raw;
}
try { return await cipher.decrypt(raw.slice(SEALED_PREFIX.length)); }
catch { await base.removeItem(key).catch(() => {}); return null; }   // also on "key unreadable"
// secure-storage.ts:13, 32
const saved = await SecureStore.getItemAsync(KEY_NAME);
const bytes = await aesDecryptAsync(AESSealedData.fromCombined(sealed), await storageKey());
Why it matters
The queued writes are the data round 1's Critical fix set out to protect. A real Keystore reset makes them unreadable anyway. A temporary read failure should not destroy them.
Recommendation
Delete only when the key loaded and decryption failed (a wrong key or a tag mismatch). If the key cannot be loaded, throw a KeyUnavailableError and keep the sealed value. In OutboxQueue.load, on a load error, keep new writes in memory and do not persist until a read succeeds. A retry on the next foreground can merge them, the same way discardSaved already works. Drop the background re-seal; the next setItem seals the value anyway. Add tests where storageKey rejects once and then succeeds.

CQ-031 · Deleting an account during the hourly job run recreates its database and a backup

Low · Data lifecycle / privacy · Effort S · New · Reproduced
Where
apps/api/src/jobs/scheduler.ts:37-40, apps/api/src/db/user-registry.ts:171-181, 208-214
What's wrong
runHourlyJobs takes deps.users.list() once and then yields before each user. If DELETE /auth/account lands during the run, the loop still reaches the deleted user. lease() then calls data(), which opens (and so creates) a fresh users/<id>.db and seeds it. The backup job then writes backups/users/<id>/app-YYYY-MM-DD.db, and job_runs gets rows for a user who no longer exists.
Evidence
$ bun probe-delete.ts   (runHourlyJobs started, then users.remove(gone))
db file right after delete: false
db file after job run: true
backups for deleted user: [ "app-2026-10-04.db" ]
users row: gone
Why it matters
The recreated files hold only seeded defaults, so no personal data comes back. They are orphans that nothing will ever clean up, though, and they make "we delete your account" less exact.
Recommendation
Re-check deps.users.find(user.id) after the yield, and skip the user if it is gone. Give data() an { create: false } mode for existing users, so it never creates a file for a missing registry row.

CQ-032 · Migration 0004 has no clean-up for rows that break the new CHECKs

Low · Data layer / migrations · Effort S · New · Unverified (no production data)
Where
apps/api/drizzle/0004_constraints.sql:1-7 (it clears only dangling FKs), apps/api/src/db/client.ts:18-35
What's wrong
Each rebuild copies rows with INSERT INTO __new_x SELECT … FROM x. If one existing row breaks a new CHECK, the whole migration aborts and openDatabase throws. That user's every request then returns 500, and through CQ-027 the job loop rejects too. At least one way to create such a row existed before this release and still exists: an event PATCHed through the API with ends_on < starts_on (see CQ-030). migrations.test.ts covers a populated database with valid rows only.
Why it matters
Migrations run lazily the first time each user's database is opened, so a bad row shows up as "the app is broken for me" with nothing in the logs that points at the migration.
Recommendation
Normalise known violators before the rebuild, for example UPDATE events SET ends_on = starts_on WHERE ends_on < starts_on. Run the migration against copies of the production backups before deploying. Log the migration error with the user tag when openDatabase fails.

5.2 Security & sessions

CQ-029 · Token refresh revokes the old session at once; concurrent 401s can sign the phone out

Medium · Security / session handling · Effort S · New · Unverified on device (timing)
Where
apps/api/src/modules/auth/routes.ts:60-64, apps/mobile/src/lib/auth.ts:81-91, 139-173, apps/mobile/src/lib/http.ts:45-53, apps/mobile/src/lib/event-stream.ts:39
What's wrong

The refresh and the screen refetches both start on AppState "active". After 24 h, refreshSessionIfStale() posts to /auth/refresh, and focusManager refetches every stale query with the same old token at the same moment. The server revokes the old session as soon as it has issued the new one. Any of those GETs whose requireAuth runs after the revoke gets 401 session_expired.

On the phone, saveSession awaits three Keystore writes before it switches tokenStore. A 401 for the old token that arrives in that window passes the ky hook's "is this the current token?" check, so expireSession() runs and the login screen appears. If this happens before line 161, the refresh's own tokenStore.get() === token check fails and the new token is thrown away. If it happens during saveSession, the delete of TOKEN_KEY can run after the write, and the next cold start opens on login.

event-stream.ts:39 calls reportUnauthorized() on any 401 without the token check.

Evidence
// api auth/routes.ts:60-64
.post("/refresh", requireAuth(deps), async (c) => {

5.3 Performance

CQ-034 · The owner's usage report opens every user's database in one request

Low · Performance / scalability · Effort S · New
Where
apps/api/src/modules/ai/usage-report.ts:67-79
What's wrong
For the owner, GET /ai/usage calls deps.users.data(user) for every user, synchronously and without a lease. Each first open runs migrations and seeding on the event loop. The handle cache's over-limit sweep closes only handles idle for 30 s or more, so a single call can push the open count far past 50. It keeps 2 to 3 file descriptors per database, with WAL, until the next sweep.
Why it matters
It undoes the CQ-013 fix exactly where the user count is largest. With open sign-up, a few hundred accounts would come near the default 1024 file-descriptor limit and block requests while the report runs.
Recommendation
Use lease(user) plus release({ closeIfOpened: true }) as the jobs do, with a yield between users. Better still, record per-user monthly AI cost in users.db when usage is logged, so the report needs no user database at all.

CQ-016 · /sync/changes still returns every changed row with no limit (carried over)

Low · Performance · Effort S · Partially fixed
Where
apps/api/src/modules/sync/routes.ts:16-37, apps/mobile/src/lib/sync-changes.ts:38-62
What's wrong
The endpoint now has a client and indexes, but it still reads every row with updated_at > since from 20 tables into one JSON body. pullChanges only needs the table names, and the assistant recovery needs only rows from a short window. A phone that comes back after weeks offline, or any caller sending since=0, gets the whole database.
Why it matters
Memory and payload grow with history. Data volumes are personal-scale today.
Recommendation
Add ?tables=only (counts per table) for pullChanges, and cap rows per table, for example 500 with a more: true flag that makes the phone refresh everything.

CQ-024 · The riskiest new client and job paths have no tests (carried over)

Low (was Medium) · Testing · Effort M · Partially fixed
Where

What's wrong
The owner moved the rules into pure modules and tested them well: outbox-queue, outbox-policy, session, encrypted-storage.
