1. Executive summary

58 / 100 overall QA score

The static gates are clean: Biome reports no diagnostics, TypeScript passes in all three workspaces, and all 185 tests pass (API 100, shared 71, mobile 14). Money is stored as integer minor units, each user has a separate SQLite file, every API route except /health, the public pages and /auth/google requires a token, and the safe-to-spend formula matches the spec's own worked example. Those choices are sound.

The weak spot is the offline write path, which the product promises and which the tests never touch. Queued writes are dropped after three quick retries when the phone has a network but cannot reach the server, and they are dropped at once on any 5xx. An edit made offline to a record that was also created offline is silently thrown away when the queue replays. An expired 30-day session wipes whatever is still queued. On the capture side, Bangla digits are not parsed, so “চা ২০” is saved as a task and never reaches the AI fallback. Six further High issues (bill pay replay, budget rollover, offline timer, app-lock bypass and two of the above) all go against the spec's “Honest numbers” principle.

4.1 Offline sync & data integrity

QA-001 · The offline outbox gives up and discards writes when the server is unreachable or returns 5xx

Critical Category: Offline / data loss Effort: M

Where: apps/mobile/src/lib/query-client.ts:L55-L58 (retry policy), :L83-L85 (online = “has a network”), apps/mobile/src/lib/http.ts:L69, apps/mobile/src/lib/api.ts:L64; apps/mobile/src/app/_layout.tsx:L88-L91 (persistence).

What's wrong: Every write goes through the ["outbox"] mutation. Its retry policy is !(error instanceof ApiError) && count < 3. TanStack only pauses a mutation when onlineManager reports offline, and here “online” means state.isConnected !== false. When the phone has Wi-Fi or mobile data but the API can't be reached (VPS down, pm2 restart, captive portal, weak signal), the request fails with ServerUnreachableError, is retried 3 times over about 7 s, then errors for good. The entry leaves the queue and only a toast remains. Any 5xx (Nginx 502 during a restart, a 500) is an ApiError, so it is not retried at all. A mutation that is running or retrying (not paused) is also not persisted by the default shouldDehydrateMutation, so killing the app mid-retry loses it too. The README promises the opposite: “Failed requests retry on their own”, “every write goes through one queue that replays in order after a restart”.

// query-client.ts L55-58
queryClient.setMutationDefaults(["outbox"], {
  mutationFn: (request: OutboxRequest) => send(request.method, request.path, request.body),
  scope: { id: "outbox" },
  retry: (count, error) => !(error instanceof ApiError) && count < 3,
// L83-85
onlineManager.setEventListener((setOnline) =>
  NetInfo.addEventListener((state) => setOnline(state.isConnected !== false)),

Evidence: code reading plus TanStack Query 5.104.1's canFetch (node_modules/@tanstack/query-core/build/modern/retryer.js:L9-L11), which only pauses when onlineManager.isOnline() is false. Unverified on device. Steps: put the phone on Wi-Fi, stop the API (pm2 stop), log “cha 20”, wait 10 s, start the API. Expected: the expense syncs. Predicted: a “Couldn't save the transaction” toast, and the expense never reaches the server.

Why it matters: Quick capture is the core flow, and the owner logs in short bursts on rickshaws and at shop counters, exactly where reachability is flaky. Lost expenses break “Honest numbers”, and the user isn't told what was lost beyond a passing toast.

Recommendation: Treat network errors, timeouts, 408/429 and 5xx as “pause and retry later”. Retry forever with capped backoff, and give up only on 4xx validation errors. Persist the queue yourself, or set dehydrateOptions.shouldDehydrateMutation: () => true for the outbox key. Keep any permanently failed write in a “Needs attention” list that the user can retry or edit.

retry: (count, e) => !(e instanceof ApiError) || e.status >= 500 || e.status === 429,
retryDelay: (n) => Math.min(60_000, 1000 * 2 ** n),

QA-002 · An offline edit to a record created offline is silently discarded on replay

Critical Category: Sync / last-write-wins Effort: S

Where: apps/api/src/lib/crud.ts:L71-L92; every sheet that sends updatedAt: editTime(), e.g. apps/mobile/src/features/tasks/task-sheet.tsx:L179, features/money/transaction-sheet.tsx:L152.

What's wrong: create() stamps updatedAt with the server's clock when the queue replays. The following PATCH carries the phone's edit time from when the user actually made the edit, which is earlier. update() returns the row unchanged when editedAt < current.updatedAt, with status 200 and no error. Create a task or transaction offline, fix a typo or the amount, reconnect later, and the fix is lost. The optimistic cache shows the edit until the next refetch, then it reverts.

// crud.ts L82-85
update(id: string, values: UpdateValues<T>): Row {
  const current = service.get(id) as Row & { updatedAt: number };
  const { updatedAt: editedAt, ...changes } = values;
  if (editedAt !== undefined && editedAt < current.updatedAt) return current;

Evidence (reproduced): create task Buy milk, PATCH title with an edit time 1 min after creation, replayed 2 h later → PATCH status: 200, title after replay: "Buy milk".

Why it matters: Corrections to money entries vanish silently, which breaks the reconciliation promise. It happens on the normal path: offline capture, then a fix.

Recommendation: Let the client send its own createdAt/updatedAt on create (server time via editTime()) and store it, or have create() set updatedAt = min(now, client edit time). Add a replay test: create, then edit, then replay much later.

QA-003 · An expired session or tapping “Sign out” wipes queued offline writes

High Category: Offline / auth Effort: M

Where: apps/api/src/modules/auth/routes.ts:L11 (30-day token, no refresh); apps/mobile/src/lib/http.ts:L49; apps/mobile/src/lib/auth.ts:L103-L111; apps/mobile/src/lib/user-data.ts:L20-L30; features/settings/account-section.tsx:L38.

What's wrong: The JWT expires after 30 days and nothing refreshes it. The first 401 calls signOut(), which runs clearUserData(): queryClient.getMutationCache().clear() plus removal of every non-device AsyncStorage key. Any writes still queued (for example after a day offline that happens to cross day 30) are deleted before they are sent. The Settings “Sign out” button does the same with no check of usePendingWrites().

// auth.ts (mobile) L111
connectAuth({ token: () => tokenStore.get(), onUnauthorized: () => void signOut() });
// user-data.ts L21-22
await queryClient.cancelQueries();
queryClient.getMutationCache().clear();

Why it matters: Silent data loss on a predictable schedule, once a month.

Recommendation: Issue a sliding session: refresh when less than 7 days remain, or return a new token in a header. On 401, pause the outbox and ask the user to sign in again without clearing it, and replay after re-authenticating as the same user id. Before a manual sign-out with pending writes, warn the user and offer to sync first.

QA-004 · An offline timer start records the reconnect time, and the matching stop is rejected

High Category: Offline / time tracking Effort: S

Where: apps/mobile/src/features/time/time-tracking.tsx:L122-L127; apps/api/src/modules/time-entries/service.ts:L94, :L104-L110; also features/timer/running-timer-bar.tsx:L53-L58 (stop uses the phone's Date.now(), not editTime()).

What's wrong: The time-tracking Start button sends no startedAt, so the server uses its own now, which is the replay time. The Stop that follows carries the real tap time. That is earlier than the server's start, so the server answers 400 Stop time must be after the start, the outbox drops the stop, and the timer keeps running on the server. The focus screen does send startedAt, so only manual time tracking is affected.

Evidence (reproduced): start offline, stop 45 min later, replay 2 h later → start 201 startedAt - tapStart (min): 120; stop 400 {"error":{"code":"bad_request","message":"Stop time must be after the start"}}; still running on server: true.

Why it matters: Tracked hours feed the effective hourly rate and cost-in-hours. The spec says “tracked hours always reconcile”.

Recommendation: Always send startedAt: editTime() on start and endedAt: editTime() on stop. Make stop target the entry id (POST /time-entries/:id/stop) so a replay is idempotent.

QA-005 · Retried action endpoints aren't idempotent and show false error toasts

Low Category: Sync / idempotency Effort: S

Where: apps/api/src/modules/shopping/routes.ts:L55-L66 (checkout → 400 “Tick at least one item first” on replay); time-entries/service.ts:L106 (stop → 409); lib/crud.ts:L101-L104 (restore → 409 “is not deleted”).

What's wrong: If the request reached the server but the response was lost to a timeout, the outbox (or a double tap) sends it again. These endpoints reject the second call with a 4xx, and MutationCache.onError shows “Couldn't …” even though the first call succeeded.

Why it matters: The user is told something failed when it didn't, may redo it by hand, and ends up with duplicates.

Recommendation: Key these actions on a client id. For example, checkout with an already-used transactionId returns the existing transaction, and restore of a live row returns 200.

QA-006 · /sync/changes exists but the app never uses it; every write refetches everything

Low Category: Sync / spec traceability Effort: M

Where: apps/api/src/modules/sync/routes.ts:L11-L31; apps/mobile/src/lib/query-client.ts:L23-L27 (invalidateQueries() with no filter, 250 ms after every write). A grep for sync/changes or sync.changes in apps/mobile/src finds nothing.

What's wrong: The spec lists /sync/changes for refreshing the offline cache. The app instead invalidates every query after each write, and screens that aren't open keep stale data until they're next opened online.

Why it matters: More data used on mobile, and stale offline screens after edits made through the assistant or on another surface. Low impact for one user.

Recommendation: Either remove the endpoint from the spec and README, or use it on reconnect to patch cached lists.

4.2 Money, budgets & bills

QA-007 · Replaying “Paid” advances a bill's due date twice, skipping a whole period

High Category: Money / idempotency Effort: S

Where: apps/api/src/modules/recurring/service.ts:L95-L146; callers apps/mobile/src/features/today/next-up.tsx:L35-L46, features/money/recurring-sheet.tsx:L107-L124.

What's wrong: pay() inserts the transaction with onConflictDoNothing(), so it is idempotent on transactionId, but it then always runs base.update(id, { nextDueAt: advance(item) }). A retried request moves the due date forward again. Separately, the Today “Paid” button generates a fresh newId() on every tap and doesn't remove the row optimistically, so a double tap while offline logs the bill twice. It also routes only income in a foreign currency to the sheet, so a USD bill paid from Today fails with “Enter the USD → BDT rate”.

// recurring/service.ts L123-L143 (trimmed)
db.insert(transactions).values({ id: transactionId, ... }).onConflictDoNothing().run();
...
const updated = base.update(id, { nextDueAt: advance(item, timeZone), overdueAt: null });

Evidence (reproduced): bill due 5 Oct, pay twice with the same transactionId → first pay nextDue "2026-11-05…", replay nextDue "2026-12-05…", expense rows: 1.

Why it matters: November's bill vanishes from Today and from notifications, which is the late-fee scenario the feature exists to prevent.

Recommendation: When transactionId already exists with recurringId = id, return the current state without advancing. Store the paid occurrence date on the transaction and advance only from that date. On Today, hide the row optimistically and disable the button after one tap.

QA-008 · Budget rollover stops after the first month that inherits limits

High Category: Money / budgets Effort: S

Where: apps/api/src/modules/budgets/service.ts:L73-L91 (inheritance), :L125-L139 (rollover).

What's wrong: A month with no budgets of its own inherits the latest earlier month's rows. Rollover reads the previous calendar month's own rows via budgetsFor(deps, previousMonth), and those are empty when the previous month was itself inherited. Set budgets once in September with rollover on: October carries in, but November, December and later carry nothing, while the line still shows rollover: true. Unspent money silently disappears from flexible-left and therefore from safe-to-spend.

// L125-L139 (trimmed)
const previousMonth = addMonths(month, -1);
const previousBudgets = new Map(budgetsFor(deps, previousMonth).map(...)); // ignores inheritance
const carriedMinor = budget?.rollover && previous?.rollover
  ? Math.max(0, previous.limitMinor - (previousSpent.get(cat.id) ?? 0)) : 0;

Evidence (reproduced): 2026-10 inherited=true {"limit":300000,"carried":300000}, 2026-11 inherited=true {"carried":0,"rollover":true}, 2026-12 … {"carried":0}.

Why it matters: The tested path (re-saving budgets each month) works, but the default path of setting budgets once does not. The daily number is understated.

Recommendation: Use effectiveBudgets(deps, previousMonth).rows for the previous month. Also decide whether carry should compound (today it ignores the previous month's own carry). Add a 3-month inheritance test.

QA-009 · Foreign-currency spending is counted as taka in budgets and safe-to-spend

Medium Category: Money / currency Effort: M

Where: apps/api/src/lib/money-queries.ts:L61-L109 (spendingRows sums amountMinor across accounts), modules/budgets/service.ts:L94-L108.

What's wrong: The spec allows any account to hold another currency, and the test fixtures include a USD “Payoneer” account. spendingRows ignores the account currency, so $50 (5,000 cents) adds 5,000 poisha (৳50) to the flexible bucket. Net worth handles this correctly by excluding foreign accounts (insights/summary.ts:L120-L141); budgets don't.

Evidence (reproduced): after a $50 USD Food expense, spentTodayMinor: 5000 and leftToday 42800 → 37800 (a ৳50 drop instead of roughly ৳6,000).

Why it matters: Card or Payoneer spending is under-reported by about 120×, so safe-to-spend overstates what's left.

Recommendation: Either exclude non-default-currency accounts from spendingRows and show “+ $50 not in budget”, or store a converted baseAmountMinor at entry time, as is already done for foreign income.

QA-010 · The calculator keypad saves ৳616.67 where the spec and the code comment say ৳617

Low Category: Money / spec mismatch Effort: S

Where: apps/mobile/src/components/ui/amount-keypad.tsx:L18, :L44-L46; packages/shared/src/money.ts:L28-L33; spec p. 13 (“I type 1850/3 … it saves ৳617”); packages/shared/test/quick-add.test.ts:L87-L90 asserts 61,667.

What's wrong: toMinor(616.666…) rounds to the poisha (61,667). The spec, and the component's own doc comment, promise whole taka.

Why it matters: Cosmetic, but it shows up as “৳616.67” on every split bill.

Recommendation: Pick one. Either round expressions with an operator to whole taka (Math.round(v) * 100) or update the spec and comment.

4.3 Capture, parsing & dates

QA-011 · Quick-add doesn't understand Bangla digits; Bangla expenses are saved as tasks and skip the AI fallback

High Category: Capture / localisation Effort: S

Where: packages/shared/src/calculator.ts:L25, :L114-L116; packages/shared/src/quick-add.ts:L172-L181, :L227-L242, :L373-L386; packages/shared/src/money.ts:L74-L82; apps/mobile/src/features/quick-add/use-quick-add.ts:L87-L96.

What's wrong: All numeric regexes use ASCII \d, and nothing in the repo maps ০-৯ to 0-9 (a search for Bangla digits in source finds only an AI voice hint). “চা ২০” isn't seen as an amount, so it falls through to parseTask. That function marks confidence "high" unless the title contains an ASCII number, and the AI parser is only called for low-confidence drafts, so it is never consulted. The same happens to “২h thesis” (not a time entry) and to parseAmountToMinor("২৫০"), which returns null.

Evidence (reproduced):

parseQuickAdd("cha 20")          {"kind":"expense","amountMinor":2000,"confidence":"high"}
parseQuickAdd("চা ২০")           {"kind":"task","title":"চা ২০","confidence":"high"}
parseQuickAdd("lunch ২৫০")       {"kind":"task","title":"Lunch ২৫০","confidence":"high"}
parseQuickAdd("রিকশা ৬০ bkash")  {"kind":"task","title":"রিকশা ৬০ bkash","confidence":"high"}
parseQuickAdd("২h thesis")       {"kind":"task","title":"২h thesis","confidence":"high"}
parseAmountToMinor("২৫০")        null

Why it matters: README promises “Bangla and English, typed or spoken, in quick-add”. A Bangla keyboard types Bangla digits by default, so the five-second expense log silently becomes an inbox task.

Recommendation: Normalise digits at the top of parseQuickAdd, evaluateExpression and parseAmountToMinor: text.replace(/[০-৯]/g, d => String(d.charCodeAt(0) - 0x09E6)). Also treat any non-ASCII-only task title as "low" confidence so Bangla text reaches the AI. Add Bangla cases to quick-add.test.ts.

QA-012 · Common words like “weekly” or “monthly” turn a task into a repeating one, and stray numbers become expenses

Medium Category: Capture / parser false positives Effort: S

Where: packages/shared/src/recurrence.ts:L365-L379 (bare daily|weekly|monthly|yearly|annually); packages/shared/src/quick-add.ts:L307-L311, :L232-L239.

What's wrong: The final recurrence pattern matches the bare adjective anywhere in the text, strips it from the title and sets an RRULE with high confidence. Separately, a trailing number in task-like text is read as an expense.

parseQuickAdd("submit weekly report") {"kind":"task","title":"Submit report","rrule":"FREQ=WEEKLY","confidence":"high"}
parseQuickAdd("pay monthly rent")     {"kind":"task","title":"Pay rent","rrule":"FREQ=MONTHLY","confidence":"high"}
parseQuickAdd("read chapter 5")       {"kind":"expense","amountMinor":500,"confidence":"low"}

Why it matters: One-off tasks start repeating forever and the title loses meaning. The preview line does show “Repeats”, which is a partial workaround. Offline, “read chapter 5” is shown as a ৳5 expense.

Recommendation: Only accept the bare adjectives at the start or end of the text, or after “every”/“repeat”. Keep the word in the title. Mark recurrence parsed from bare adjectives as "low" so the AI or the user confirms it.

QA-013 · Today doesn't roll over at midnight while open or offline, and new-day expenses don't move the card

Medium Category: Dates / midnight rollover Effort: S

Where: apps/mobile/src/lib/queries.ts:L6, :L32-L37 (key ["today","now"]); apps/mobile/src/lib/query-client.ts:L32-L34; apps/mobile/src/lib/optimistic-spend.ts:L41; apps/mobile/src/app/(tabs)/index.tsx:L17-L56.

What's wrong: Today's cache key doesn't include the date, and data refreshes only on focus or after a write. 4.4 Tasks

QA-015 · Undoing completion of a repeating task leaves a duplicate and breaks the series

Medium Category: Tasks / undo Effort: S

Where: apps/api/src/modules/tasks/service.ts:L237-L247; apps/mobile/src/features/tasks/use-task-actions.ts:L29-L43.

What's wrong: Completing a repeating task clears its rrule and creates the next copy. Undo just PATCHes status back to open, so the original stays open without its rule and the new copy also exists.

4.5 Security & access

QA-017 · The fingerprint lock is skipped on cold start: killing and reopening the app bypasses it

High Category: Security / app lock Effort: S

Where: apps/mobile/src/features/security/app-lock.tsx:L11-L41.

What's wrong: locked is initialised once with useState(enabled). On a cold start, settings come from the persisted cache, which is restored asynchronously by PersistQueryClientProvider, so on first render enabled is false and locked stays false. When settings arrive, the effect can only unlock. The lock only arms after a background → foreground transition.

const enabled = settings?.appLock ?? false;
const [locked, setLocked] = useState(enabled);       // false while settings load
useEffect(() => { if (!enabled) setLocked(false); }, [enabled]);  // never re-locks

Evidence: code reading. Unverified on device. Steps: enable App lock, swipe the app away from Recents, reopen it. Expected: fingerprint prompt. Predicted: Today opens with amounts visible.

Why it matters: This is the one privacy control for a phone handed to someone else.

Recommendation: Store the lock preference on the device (SecureStore/AsyncStorage) and read it before first render, or lock on mount until settings resolve: useEffect(() => { if (enabled) setLocked(true) }, [enabled]) for the first resolution. Optionally set FLAG_SECURE to hide the Recents thumbnail.

QA-018 · Login rate limit and bind address differ from the spec

Low Category: Security / config Effort: S

Where: apps/api/src/modules/auth/routes.ts:L24 (10 per 15 min; the spec says 5), :L27 (x-real-ip ?? "local": every caller without the header shares one bucket); apps/api/src/env.ts:L5 (HOST default 0.0.0.0; spec p. 26 says the process listens on 127.0.0.1).

Why it matters: If the README step HOST=127.0.0.1 is missed, the API is reachable on the raw port without TLS, and X-Real-IP can be forged to get past the limiter.

Recommendation: Default HOST to 127.0.0.1. Align the limit with the spec, or update the spec.

4.6 AI

QA-019 · AI guardrails are weaker than the spec: the assistant saves without confirmation and the cap is checked once per turn

Medium Category: AI / spec deviation Effort: M

Where: apps/api/src/modules/ai/prompts.ts:L46 (“Adds and edits happen right away”); spec p. 37 “Deliberately not building: Any AI feature that saves records without my confirmation” and p. 24 “each returns a draft and never saves”; apps/api/src/modules/ai/routes.ts:L95 and assistant/agent.ts:L13, :L165-L206 (one requireAi, then up to 13 “smart” calls); apps/api/src/ai/usage.ts:L59-L81 (owner never capped; the cap is a server env var, not a Settings value as the spec says).

What's wrong: The chat assistant creates and edits transactions and tasks directly. Undo exists, but a misheard Bangla voice note can change account balances before the user sees anything. The monthly cap is checked before the first model call, so one assistant turn can run 13 paid calls past the cap. For the owner there is no cost ceiling at all.

Why it matters: It conflicts with “Honest numbers” and with the spec's explicit exclusion. The cost exposure is unbounded for the owner.

Recommendation: Make the choice explicit: either update the spec, or have money writes from the assistant come back as drafts the user confirms (deletes already work this way). Re-check the cap inside the loop. Restore an owner-settable cap in Settings, even if it defaults to “none”.

QA-020 · AI calls can outlive Nginx's default 60 s proxy timeout, and bad AI output returns 500 instead of ai_error

Medium Category: AI / failure handling Effort: S

Where: apps/api/src/ai/openai-client.ts:L20 (timeout: 45_000, maxRetries: 1, so up to about 90 s+); deploy/nginx-tick-taka.conf:L10-L18 (no proxy_read_timeout, Nginx default 60 s); apps/mobile/src/lib/http.ts:L7 (client waits 90 s); apps/api/src/modules/ai/parse.ts:L169, :L190, :L272 (schema.parse runs outside callAi); middleware/error-handler.ts maps unknown errors to 500 internal_error.

What's wrong: A slow receipt scan or plan-day call that retries once gets a 504 HTML page from Nginx, which the app shows as “Request failed (504)”. The model is still billed and no usage is logged, because logUsage only runs on success. Output that fails the Zod schema surfaces as a generic server error rather than the documented fallback code.

Evidence: config and code reading. Unverified against a live Nginx.

Recommendation: Set proxy_read_timeout 120s; for /ai/, or cut the server budget to under 55 s in total (maxRetries: 0, 25 s). Move schema.parse inside callAi so every AI failure is a 502 ai_error.

QA-021 · Assistant writes continue on the server if the stream drops, without the client showing Undo

Low Category: AI / streaming Effort: M Unverified

Where: apps/api/src/modules/ai/routes.ts:L93-L125 (no abort handling around aiAssistant); apps/mobile/src/lib/event-stream.ts:L52-L58 (a read error becomes ServerUnreachableError).

What's wrong: When the phone loses the connection mid-turn, nothing visible stops the agent loop from carrying on with writes through dispatch. The client never receives the action events, so it can't offer Undo. Not reproduced; Hono's behaviour on client abort for streamSSE wasn't tested.

Recommendation: Stop the loop on stream.onAbort. After a dropped stream, have the client fetch “recent assistant actions” so Undo is still available.

4.7 Client platform & jobs

QA-022 · Reminder scheduling has gaps, and permission denials are silent

Medium Category: Client / notifications Effort: M

Where: apps/mobile/src/features/notifications/use-notification-scheduler.ts:L13-L31, :L91-L99; apps/mobile/src/lib/notifications.ts:L12-L17; apps/mobile/src/lib/receipts.ts:L19-L22.

What's wrong: (1) Task reminders are planned only for tasks whose doAt falls between now − 1 day and now + 8 days, so an inbox task with a reminderAt but no doAt never rings. (2) Rescheduling runs only after Today refetches, so if the app isn't opened for about 9 days, no reminders exist. (3) A denied notification or camera permission returns early with no message and no link to Settings. (4) Errors in reschedule are swallowed (.catch(() => {})).

Why it matters: The spec relies on phone-scheduled reminders, with no push. Missed bill and task reminders are invisible failures.

Recommendation: Query tasks by reminderAt range rather than doAt. Schedule on a background fetch as well as on app open. When permission is denied, show a one-line banner in Settings with “Open settings”.

QA-023 · Nightly jobs have no catch-up when the server is down at :05

Low Category: Server / scheduled jobs Effort: S

Where: apps/api/src/jobs/scheduler.ts:L17-L43.

What's wrong: Each user's backup runs only if the process is alive at xx:05 during local hour 3, and overdue marking only during hour 0. A restart or deploy at that moment skips the day, and nothing records or retries it. Overdue status is computed from dates anyway, so only the overdueAt flag and the backup are affected.

Recommendation: On each hourly tick, back up if today's file is missing and the local hour is ≥ 3. Log the last success in the settings table under an internal _ key.

QA-024 · SMS auto-capture is missing but still listed in the spec checklist and implementation plan

Low Category: Traceability / docs Effort: S

5. Strengths (keep these)

  • Money is integers end to end. toMinor rounds half away from zero with an epsilon (money.ts:L28-L33), splitEvenly conserves totals, and balances and budgets are computed from transactions, never stored.
  • Safe-to-spend matches the spec. Flexible-left is taken as of the start of today, divided by days left including today, and floored to whole taka (finance.ts:L20-L24). The API test reproduces the spec's ৳640 example exactly.
  • Client-generated ULIDs make creates idempotent (crud.ts:L71-L80, debts, goals, balance check, receipts), and the phone stamps edits in server time via the x-server-time offset. Both are the right foundations; QA-002 and QA-007 are gaps in applying them, not in the design.
  • Per-user database isolation is enforced in the middleware (runAsUser) and covered by users.test.ts, and the auth middleware wraps the whole API.
  • AI failures degrade gracefully in quick-add. callAi turns provider errors into 502 ai_error, the cap and off switch have their own codes, and use-quick-add.ts silently keeps the on-phone draft.
  • Time-zone handling is careful. Instants are UTC, local dates are strings, zonedTimeToUtc does two-pass offset resolution, jobs run per user time zone, and Bangladesh's Sun–Thu work week is honoured.
  • Clean gates: 0 lint diagnostics, 0 type errors, 185 passing tests with meaningful assertions and an injectable clock.
