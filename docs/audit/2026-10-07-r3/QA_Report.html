5.1 Offline sync & local storage

QA-301 · When the server keeps failing on a create, the edits queued behind it get 404 and are dropped, and Retry brings back the old version

MediumCategory: Offline / data lossEffort: MReproduced

Where: apps/mobile/src/lib/outbox-queue.ts:L247-L254 (park after STUCK_AFTER), :L90-L98 (retryStuck appends to the end), :L284-L292. outbox-policy.ts:L70-L79 (404 → reject), :L86-L96. components/ui/sync-status.tsx:L27-L59 (one Retry per entry). apps/api/src/db/user-registry.ts:L186-L192 (a database that won't open is a plain 500).

What's wrong: Parking a write that failed 8 times lets the writes behind it go, but some of those depend on it. A PATCH or DELETE of a record whose create is parked gets 404. classifyFailure calls that final, so the edit is dropped with a toast. When the user later taps Retry on the parked create, the record is created as it was first typed. The same happens to a transaction whose new account is parked (400 invalid_reference). If every request 500s for about two minutes (a user DB that won't open, a full disk, a bad deploy that still answers), each queued write is parked in turn. The user then has to tap Retry once per write, and each retry goes to the back of the queue. Retrying an edit before its create drops the edit too.

// Real OutboxQueue; the API answers POST /tasks with 500 eight times, then works.
enqueue POST  /tasks          {id, title: "Call bank"}
enqueue PATCH /tasks/{id}     {title: "Call bank about card", updatedAt}
STUCK-CREATE: stuck POST /tasks | rejected PATCH tasks | stuck=["POST"]
              | after Retry: 200 title="Call bank" | queue size 0

Why it matters: The edit is lost for good. It was only ever on the phone, and the phone has already said it couldn't save it, which is a confusing message for an edit to something the user can still see. This happens in exactly the situation parking was built for: a server bug or outage.

Recommendation: When parking, also park every queued entry that names the same record id, in its path or as its body id, plus anything whose body references it. Retry and Discard should then act on the whole group, in order. Add “Retry all”, which re-queues the parked entries in their original order. On the server, return 503 (not 500) when a user's database can't be opened, so the phone waits instead of parking.

QA-304 · Writes queued before the outbox has loaded, including the widget hand-over, exist only in memory

LowCategory: Offline / start-upEffort: SUnverified on device

Where: apps/mobile/src/lib/outbox-queue.ts:L169-L179 (enqueue), :L320-L322 (persist is a no-op until loaded), :L142-L150 (unreadable saved queue: stays unloaded). features/widget/use-widget-sync.tsx:L43-L54. app/_layout.tsx:L80-L84 (startOutbox() fire-and-forget).

What's wrong: persist() returns early until the saved queue has been read, so it can't overwrite it, and writes queued before then live only in memory. On start-up, useWidgetSync reads the widget's offline list, enqueues each log, and then trims those logs from the widget's own storage. It doesn't wait for the outbox to load or for its save to finish. While the storage key can't be read, the outbox stays unloaded indefinitely. In that state every new expense, and every widget log handed over, exists only in memory, even though the screen says it's saved on the phone.

// use-widget-sync.tsx L45-L48
const pending = await readPendingLogs();
for (const log of pending)
  send({ method: "POST", path: "/transactions", body: { ...log, type: "expense" } });
if (pending.length) await removePendingLogs(pending);   // no await on the outbox's own save

Why it matters: If the app is killed or crashes in that window, those expenses are gone. Normally the window is a few hundred milliseconds. With a Keystore that won't unlock, it lasts as long as the app is open.

Recommendation: In useWidgetSync, await startOutbox(), skip the hand-over while outbox.savedUnreadable, and await outbox.flushed() before removePendingLogs. While the saved queue is unreadable, write new entries to a separate side key (for example tt.outbox.pending) that load() merges. Say “not saved yet” in the status line.

QA-305 · A storage-key hiccup at start-up still deletes the encrypted screen cache

LowCategory: Storage / offlineEffort: SUnverified on device

Where: apps/mobile/src/lib/query-client.ts:L74-L89 (persister over secureStorage). encrypted-storage.ts:L60-L63 (rethrows KeyUnavailableError). TanStack persistQueryClientRestore (node_modules/@tanstack/query-persist-client-core/build/modern/persist.js), which calls persister.removeClient() whenever restoreClient throws.

What's wrong: The round-2 fix keeps sealed values when the key can't be read, and the outbox honours that. The query cache doesn't: restoreClient rethrows, and TanStack responds by discarding the persisted cache. So if the key can't be read once on a cold start, the offline copy of balances, tasks and today is deleted. This contradicts the module's own promise: “the sealed value stays as it is, to be read on a later try”.

Why it matters: Opening the app offline after such a start shows empty screens until it reaches the server. No server data is lost.

Recommendation: Wrap restoreClient so it catches KeyUnavailableError and returns undefined, which means no cache rather than a broken one. Then retry the restore on the next foreground. Add a unit test with a cipher that throws KeyUnavailableError.

QA-307 · The full JSON export is left in the app's cache folder after sign-out and account deletion

LowCategory: Privacy / data at restEffort: S

Where: apps/mobile/src/features/settings/use-export-data.ts:L14-L22. lib/user-data.ts:L21-L33 (clearUserData clears AsyncStorage and the caches, not files).

What's wrong: The export (every table, notes and amounts included) is written as plain JSON to Paths.cache/tick-taka-export-YYYY-MM-DD.json so it can be shared, and it is never deleted. The new delete-account page suggests exporting right before deleting. clearUserData, which promises to leave “nothing of the signed-out user on the phone”, doesn't touch that file. The whole export is also parsed into memory and re-stringified (send("GET", "/export")), even though the server streams it to avoid exactly that.

Why it matters: A full copy of the user's money history stays on the phone, unencrypted, after they sign out or delete the account. Android's cache folder is app-private, so the risk is limited to device dumps and rooted phones.

Recommendation: Delete the file once shareAsync resolves, and sweep tick-taka-export-*.json in clearUserData. Download straight to a file (File.downloadFileAsync with the auth header) instead of parsing the JSON.

5.2 AI assistant

QA-302 · Saving an old “set budget” draft, or its Undo, overwrites the whole month and reverts other budget lines

MediumCategory: AI / money correctnessEffort: S–MReproduced

Where: apps/api/src/modules/ai/assistant/actions.ts:L160-L193 (snapshot of all lines → draft body and undo). modules/budgets/service.ts:L249-L283 (putBudgets: “Replaces a month's budgets … others in the month are removed”). apps/mobile/src/features/assistant/use-assistant.ts:L220-L236 (drafts stay pending in the saved chat, with no expiry).

What's wrong: To change one line, set_budget reads every line of the month and puts the full list into the draft body (PUT /budgets {month, budgets:[…all…]}). The Undo is the full list from before. A draft can sit in the chat for days. If the user changes any other budget in that month first (in the Budgets screen, or with another draft), Save writes back the old values for every other line, and deletes lines added in the meantime. The card only says “Set the Food budget for 2026-10 · ৳8,000”. The same happens to the Undo of a saved, or non-draft, set_budget.

Fun = ৳2,000 when the draft "Food 8000" is made
user sets Fun = ৳3,000 in Budgets an hour later
Save on the old draft:  PUT /budgets → 200 → Food=800000, Fun=200000   (Fun silently back to ৳2,000)

Why it matters: Budgets drive the daily safe-to-spend number, which is the product's core number. A confirmed one-line change silently undoes another one, with nothing on screen to show it.

Recommendation: Give the API a one-line upsert, for example PUT /budgets/:month/:categoryId {limitMinor, rollover} and DELETE for removal. Make the draft and its Undo touch only that line, with Undo restoring the line's previous value or deleting it. Until then, re-read the month at Save and re-apply only the changed line on the phone.

QA-306 · The assistant's update_settings applies any setting with no Undo, including turning off App lock

LowCategory: AI / safetyEffort: SReproduced

Where: apps/api/src/modules/ai/assistant/actions.ts:L216-L221. Tool description at tools.ts:L107. The runner's own contract (“Every change … is recorded with a way to undo it”) is at tools.ts:L147-L150.

What's wrong: update_settings forwards whatever fields the model sends to PATCH /settings. There's no allow-list and no draft, and the action is recorded without an undo. Round 2 recommended both. Zone validation now stops the crash, but the model can still switch appLock off, change lockAfterMinutes, turn AI features off (which also removes the assistant), or change defaultCurrency, which decides which accounts count toward safe-to-spend. A mis-heard voice note or text injected into a note the assistant reads is enough.

update_settings {defaultCurrency:"USD", appLock:false} with draftMoney:true
→ drafts 0, actions [{"summary":"Changed settings: defaultCurrency, appLock"}]   (no undo)
→ settings now: defaultCurrency=USD appLock=false

Why it matters: A security setting changes without a tap. There's no Undo, and no screen says what the value used to be.

Recommendation: Allow-list the low-risk keys (theme, dailyTaskGoal, focus, quietHours, vacationMode, weeklyFocus…). Make appLock, lockAfterMinutes, ai, defaultCurrency, defaultAccountId and timeZone drafts, or refuse them. Record an Undo with the previous values, the same way update does.

5.3 Money & time

QA-303 · Undo of a bill payment whose reply was a replay deletes the expense but leaves the due date a month ahead

LowCategory: Money / UndoEffort: SReproduced

Where: apps/api/src/modules/recurring/service.ts:L100-L109 (a replay returns previousDueAt: null). apps/mobile/src/features/money/recurring-pay.ts:L14-L31, L41-L59.

What's wrong: The new Undo for “Paid” uses the reply's previousDueAt to move the due date back. When the first reply is lost (a timeout on a slow network after the server has committed), the outbox resends the same transactionId. The server treats that as a replay and answers with the logged transaction but previousDueAt: null. undoPayRequests then only deletes the expense.

first pay → previousDueAt 2026-10-05 (reply lost) | replay → previousDueAt null, same transaction
undo requests: DELETE transactions
after Undo: nextDueAt 2026-11-05 | expenses 0      (October's bill now looks paid)

Why it matters: After Undo the bill disappears from Today until next month, so the user may never pay October's bill. The trigger is narrow: a lost reply followed by Undo while the snackbar is still up.

Recommendation: On a replay, return the due date the logged payment moved from. It can be stored on the transaction (for example recurring_due_at) or derived by stepping the rule back once from the current nextDueAt. Alternatively, add POST /recurring/:id/unpay {transactionId} that does both steps on the server in one transaction.

QA-308 · Ten client spots work out “today” or “this month” in Asia/Dhaka, whatever the time-zone setting says

LowCategory: Time zonesEffort: S

Where: toLocalDate(Date.now()) / toLocalMonth(Date.now()) with no zone in features/habits/queries.ts:L5, money/budgets-screen.tsx:L32, app/budget-edit.tsx:L9, review/monthly-review.tsx:L26, review/payday-plan.tsx:L26, review/review-home.tsx:L77, money/events-screen.tsx:L31, money/goal-sheet.tsx:L114, app/pick-top-three.tsx:L7, app/plan/day.tsx:L7.

What's wrong: The server and most screens use userTime(settings).timeZone. These ten use the shared default instead. For a user whose zone isn't Asia/Dhaka, habits are logged against the Dhaka date, and the budget editor, monthly review and payday plan open on the wrong month for up to 18 hours around midnight on the first. The “Sunday” review prompt is also off.

Why it matters: It only affects users outside Bangladesh, but the app now validates and accepts any zone, and the server already respects it.

Recommendation: Use a useToday() or useThisMonth() hook built on userTime. Add a lint rule (Biome noRestrictedImports-style, or a grep in CI) that flags toLocalDate(Date.now()) without a zone.

Appendix C — Requirement checklist used

From PRODUCT.md and the spec: log anything in under 5 s. Today answers “what now?” and “can I afford it?”. Safe to spend = flexible left ÷ days left including today, with fixed bills excluded. Amounts are integer minor units. Offline cache with queued writes sent in order, ids made on the phone, last-write-wins on updated_at. Asia/Dhaka by default for display, with local strings for habit dates and budget months. Streaks with 2 freezes a month. Reward, never guilt. Honest numbers (balances and hours reconcile). AI: rules first, a cost cap, graceful fallback, minimum data, an off switch, and never saving money without confirmation. App lock after 5 min. Receipts served only to authenticated requests. Login limited to 5 per 15 min. Bun listens on 127.0.0.1. Nightly VACUUM INTO backup keeping 14. JSON export. Local notifications with quiet hours 23:00–07:00. Bangla and English quick-add.

The round-1 fix contract adds: revocable sliding sessions with POST /auth/refresh, logout and account deletion. A 401 never clears the queue. A wipe happens only when a different user signs in. Signing out with pending writes asks first. Receipts load with a Bearer header only. The round-2 recommendations adopted since add: zone validation, per-user job isolation, a refresh grace window, CHECK→400, stuck-write parking, money drafts for budgets and amount fields, and persisting the clock offset.
