5.1 Offline sync & error handling

CQ-043 · A stuck edit holds back every later write that names its record, and Discard drops them with it

Medium · Offline sync / data integrity · Effort M · New · Reproduced (probe B)
Where
apps/mobile/src/lib/outbox-policy.ts:103-136 (writtenIds, mentionsAny), apps/mobile/src/lib/outbox-queue.ts:138-146, 260-276, 424-456, apps/mobile/src/components/ui/sync-status.tsx:19-26, 52-79
What's wrong

To fix CQ-038, a stuck write's group is defined by mention. writtenIds takes every ULID in the stuck write's path, plus id/transactionId in its body. mentionsAny then matches any later write that carries one of those ids anywhere in its path or body, up to 3 levels deep. That rule is right when the stuck write creates the record, because a later edit would get 404. It's wrong when the stuck write only edits a record the server already has: PATCH /categories/C, PATCH /accounts/A, PUT /budgets/2026-10/C (the category id is in the path), POST /recurring/R/pay. Every later expense with categoryId: C or accountId: A is set aside too, though the server would accept it, and so is every one queued after the park (parkedHeadFor).

Getting out isn't easy. Retry sends the failing head first, so the group is parked again after another 8 server faults (about two minutes). The only other way out is Discard, which drops the whole group (discardStuck), expenses included. The bar describes the group by the head's label, and labels are written as rejection messages. The row therefore reads "Couldn't save, and 2 later changes to it", and the snackbar says "Discarded “Couldn't save”". Nothing tells the user that two expenses are in the group.

Evidence
// outbox-policy.ts:132-135: any id, anywhere in path or body
export function mentionsAny(request: OutboxRequest, ids: ReadonlySet<string>): boolean {
  if (ids.size === 0) return false;
  const inPath = (request.path.split("?", 1)[0] ?? "").split("/").some((s) => ids.has(s));
  return inPath || bodyMentions(request.body, ids, 0);
}
$ bun test probe.test.ts     (stuck: PATCH /categories/C answered 500 every time)
probe B: {"STUCK_AFTER":8,"sentTransactions":0,
  "stuck":["PATCH /categories/01M4…Q50","POST /transactions","POST /transactions"]}
Two expenses in category C, one queued before the park and one after, were never sent. All three writes sit in one group.
Why it matters
Expenses are the core capture flow. While they're held back, safe-to-spend on the server, the widget and any other device are wrong. The one action that unblocks the queue throws them away. The trigger is the same as CQ-038's, a write the API keeps failing with 5xx (a server bug), so it's rare. When it happens, though, it drops money records, and the UI doesn't tell the user that's what Discard will do.
Recommendation
Make a write depend on the ids the stuck group creates, not on every id it mentions. For a stuck write that isn't a create, park only later writes to the same record (its path, or a sub-path of it). Describe the group by kind rather than by its error label, and say what Discard drops.

CQ-045 · The API's own http_error code is read by the phone as "a proxy answered", so such a write is retried forever

Low · Error handling / API contract · Effort S · New · Reproduced (probe A)
Where
apps/api/src/middleware/error-handler.ts:17-19, node_modules/hono/dist/validator/validator.js:18 (hono 4.13.13), apps/mobile/src/lib/api.ts:34-37, apps/mobile/src/lib/outbox-failure.ts:15, apps/mobile/src/lib/error-copy.ts:62
What's wrong
87daf33 made the phone tag any error body that fails errorBodySchema with code http_error, meaning "something in front of the API answered". describeFailure turns that code into {unreachable: true}. But the API already sends http_error in its own, valid envelope for every HTTPException. Hono's JSON validator throws one, HTTPException(400, "Malformed JSON in request body"), on any validate("json") route. The phone checks the code string, not whether the body parsed, so it can't tell the two apart. A permanent 400 becomes "retry forever". It never counts as a server fault, so it is never parked, and the error copy says the user is offline.
Evidence
// error-handler.ts:17-19
if (error instanceof HTTPException) {
  return c.json(errorBody("http_error", error.message || "Request failed"), error.status);
}
// outbox-failure.ts:15
if (error.code === "http_error" && error.status !== 401) return { unreachable: true };
probe A: {"code":"http_error","info":{"unreachable":true},"kind":"retry","serverFault":false}
Why it matters
Today's trigger is rare, because ky serialises the JSON itself. But it's a contract collision. Any future HTTPException, such as a body limit or a header check, would silently block its write at the head of the queue forever, and every write behind it would wait in order.
Recommendation
Give the API's code its own name (for example bad_request), or map 4xx HTTPExceptions to validation_error. On the phone, mark the "not our envelope" case with a field of its own (for example ApiError.fromProxy = true) instead of reusing a code string the server also sends. Add a test that a valid envelope with status 400 and any code is classified reject.
Effort
S

6. Strengths: keep these

  • Fixes in layers, at the root cause. The clock bug was closed in three places: the phone ignores impossible times, a bad saved offset is refused on restore, and the server stops trusting pre-2024 stamps. Any one of them would have stopped the data loss.
  • Tests that use production's inputs. A header-less 502 goes through the real ky instance. The cache test runs the real TanStack persister over the real encrypted storage, with a cipher that can be locked. The durability tests model the disk, a slow start and a failed save, and assert what ends up stored.
  • Undo that needs nothing from the reply. POST /recurring/:id/unpay takes the pay's own transactionId and dueAt, deletes only what that pay logged, and moves the date back only if that pay moved it. It's safe to repeat and can be queued offline, and the phone cancels the pay instead if it hasn't been sent yet.
  • Narrow write paths for the assistant. Budget drafts and their Undo write one line (PUT /budgets/:month/:categoryId), so a draft saved days later can't revert other lines. Settings changes go through a typed allow-list, record their previous values for Undo, and refuse the whole request if any field is off the list.
  • Durability that's explicit. durable() means "read, and saved without error". The widget hands over its offline taps against that promise, and a write queued before the saved queue is readable goes to a side key instead of overwriting it.
  • Owner's rules kept. No file is over 800 lines. There are no barrels and 0 TODOs. Every value export is used. New shared components take named variants (IconButton shape, DateField kind/span). The design rules (time zone, type scale, colour meaning) have tests that fail on a new violation.
  • Commit discipline. All 36 commits are Conventional Commits, each one logical change. 35 carry a Refs: trailer, and none has co-author or agent lines. 801dd5f is a good example: a 5-line fix with its test, and a body that explains why 413 is final.
  • Unchanged strengths. One SQLite file per user, integer money with CHECKs, zod at every boundary, typed RPC, no secrets in git (pattern scan clean), backups that check their own integrity, 0 non-null assertions, 1 justified any.
