5.1 Offline sync & data integrity

CQ-036 · A reply without x-server-time sets the phone's edit clock to 1970, and edits made until the next normal reply are lost

High · Offline sync / data integrity · Effort S · New · Reproduced (phone module and API)
Where
apps/mobile/src/lib/http.ts:73, apps/mobile/src/lib/event-stream.ts:39, apps/mobile/src/lib/server-clock.ts:20-33, apps/api/src/lib/crud.ts:83-88, apps/mobile/test/server-clock.test.ts:41-45
What's wrong

Both request paths call noteServerTime(Number(response.headers.get("x-server-time")), …) on every reply. When the header is missing, get() returns null, and Number(null) is 0, not NaN. The Number.isFinite guard therefore passes, and offsetMs becomes −(sentAt + receivedAt)/2, about −1.79 × 10¹² ms. Because that is more than 1 s away from the saved value, it is also written to AsyncStorage. From then on editTime() returns the milliseconds since that reply: −50 at first, about 60 000 a minute later.

Only the Hono app sets the header, so any reply Nginx writes itself lacks it. That includes the 502 while pm2 restarts the API (every deploy), a 504, and the 413 for an over-size body. outbox-policy.ts:89-91 already expects proxy error pages to reach the phone. The outbox keeps retrying during an outage, so a phone with queued writes is very likely to see one.

34 call sites use editTime(), and most of them stamp a write at tap time. That includes 23 PATCH updatedAt stamps, timer start and stop (time-tracking.tsx:94,134, running-timer-bar.tsx:73), undo of task moves and assistant draft saves. The server keeps whichever row is newer and answers 200 with the old one (crud.ts:85), so the edit disappears at the next refresh and no message is shown. In the first moments the stamp is negative and the write is refused with a 400 instead. The next reply that carries the header repairs the offset, but writes already queued keep their 1970 stamps. If the app is killed while the server is still down, the saved bad offset is restored on the next start.

Evidence
// http.ts:68-73
const sentAt = Date.now();
const response = await http(input, { … });
noteServerTime(Number(response.headers.get("x-server-time")), sentAt, Date.now());
// server-clock.ts:28-32
export function noteServerTime(serverTime: number, sentAt: number, receivedAt: number): void {
  if (!Number.isFinite(serverTime)) return;          // 0 passes
  offsetMs = serverTime - (sentAt + receivedAt) / 2;
// crud.ts:85 — an older edit loses, silently
if (editedAt !== undefined && editedAt < current.updatedAt) return current;

The unit test for this case passes Number.NaN (server-clock.test.ts:41-45), which is not the value the real code produces.
Why it matters
The app promises that offline edits are kept and replayed. Here a routine deploy, or any time the API is down while the phone has signal, quietly throws away renames, moves, status changes and undos made in that window. Timers started in it are saved as starting in 1970. Nothing tells the user, and nothing is logged on the server. This is not Critical only because the window is bounded by the next normal reply and because creates and deletes are not stamped.
Recommendation
// http.ts and event-stream.ts: learn only from replies that carry the header
const header = response.headers.get("x-server-time");
if (header !== null) noteServerTime(Number(header), sentAt, Date.now());
// server-clock.ts: refuse impossible values, not only NaN
const EARLIEST = Date.UTC(2026, 0, 1);
if (!Number.isFinite(serverTime) || serverTime < EARLIEST) return;
Also clamp editTime() to be at least the last stamp it returned, so it can never go backwards. Replace the NaN test with one that passes Number(new Headers().get("x-server-time")), and add one for a saved offset that is out of range.

CQ-038 · Setting a stuck write aside lets the writes that depend on it go first

Medium · Offline sync / ordering · Effort M · New
Where
apps/mobile/src/lib/outbox-queue.ts:89-98, 247-254, 284-292, apps/mobile/src/lib/outbox-policy.ts:64-79, apps/mobile/test/outbox-queue.test.ts:290-317, README.md › Notes on decisions ("replays in order")
What's wrong

Until this round the queue sent strictly in order. Now, after STUCK_AFTER (8) server faults other than 503, the head entry is parked and the loop moves on. The phone makes record ids itself (newId() in task, project, area, category, time-entry and other sheets), so the writes behind a stuck create often name that same record. If the parked write is POST /tasks {id: T}:

  • a later PATCH /tasks/T gets 404, is classified reject and is removed for good, with a snackbar;
  • a later DELETE /tasks/T gets 404, which alreadyInWantedState counts as applied;
  • Retry then sends the create after both, so the task comes back without the edits, or comes back after the user deleted it.

A parked PATCH is mostly safe, because a newer PATCH lands first and the older one loses last-write-wins when retried.

Evidence
// outbox-queue.ts:250-254
entry.serverFailures = isServerFault(failure) ? (entry.serverFailures ?? 0) + 1 : 0;
if (entry.serverFailures >= STUCK_AFTER) {
  this.park(entry, error);
  continue;                               // next entry goes, whatever it refers to
}
// outbox-policy.ts:65-66
if (request.method === "DELETE" && status === 404) return true;   // "applied"
The test for parking puts an unrelated write behind the poison one (PATCH /events/e1, then POST /tasks), so this case never runs.
Why it matters
The trigger is a server bug, not bad input, since CHECK violations are now 400s. When it happens, though, parking turns one failing write into a chain of lost or resurrected ones, which is the opposite of what it was added for. The user sees one "keeps failing" message and then a few "couldn't save" messages, with no hint that they are linked.
Recommendation
Park dependants with the write they depend on. When an entry is parked, collect the record ids it creates or edits (idsOfWrite in phone-writes.ts already extracts them). Park every later entry whose path or body names one of those ids, along with any entry queued later for the same ids. Retry and Discard act on the whole group, and discarding a parked create discards its group too. Add a test: stuck POST /tasks {id:T}, then PATCH /tasks/T, DELETE /tasks/T and one unrelated write. Only the unrelated write goes, and Retry sends the group in order.

M

CQ-039 · Two ways the outbox can still lose writes without saying so

Low · Error handling / offline sync · Effort S · New
Where
apps/mobile/src/lib/outbox-queue.ts:142-149, 320-330, apps/mobile/src/features/widget/use-widget-sync.tsx:43-54
What's wrong
  1. persist() chains every save with .catch(() => {}). If AsyncStorage refuses a write (disk full, a storage error), the queue carries on from memory, and a kill loses everything not yet sent. Nobody is told.
  2. While the saved queue is unreadable (the CQ-028 fix), new writes are held only in memory, by design. useWidgetSync hands the widget's offline expenses to the outbox and then calls removePendingLogs. At that point the only durable copy is gone, and a kill before the key becomes readable loses those expenses. The same short window exists at every start, before load() finishes.
Evidence
// outbox-queue.ts:320-329
private persist(): void {
  if (!this.loaded) return;                       // unreadable: memory only
  …
  this.saving = this.saving.then(() => this.deps.save(state)).catch(() => {});
// use-widget-sync.tsx:45-48
const pending = await readPendingLogs();
for (const log of pending) send({ method: "POST", path: "/transactions", … });
if (pending.length) await removePendingLogs(pending);   // durable copy deleted here
Why it matters
"Log anything in under five seconds" is the spec's core promise, and the widget is the fastest way in. Both paths need an unusual condition (a storage failure, or a kill while the key can't be read), but when they happen the loss is silent.
Recommendation
In persist(), catch once, log, notify(), and expose a flag the sync bar shows. In useWidgetSync, await outbox.flushed() and delete the widget's copies only when the queue is loaded and not savedUnreadable. Otherwise leave them for the next start: each log carries a client id, so a repeat is refused as a duplicate rather than saved twice.

CQ-037 · A Keystore read failure at start still costs the cached screens, and the next save can go to disk unencrypted

Low · Data integrity / security (client) · Effort S · New · Unverified on device (how often)
Where
apps/mobile/src/lib/query-client.ts:75-89, node_modules/@tanstack/query-persist-client-core/build/modern/persist.js:32-38 (5.104.1), apps/mobile/src/lib/encrypted-storage.ts:70-79, apps/mobile/src/lib/secure-storage.ts:95-106, apps/mobile/src/lib/session-manager.ts:66-76, 112-126
What's wrong

The outbox now handles KeyUnavailableError correctly. The query-cache persister does not. restoreClient calls secureStorage.getItem, which throws, and TanStack's persistQueryClientRestore catches any error and calls removeClient(), which deletes tt.query-cache. The next throttled save then calls setItem. If the key still can't be read, encryption fails and the fallback writes the whole cache (balances, transactions, notes) in plain text until a later write seals it again. The only signal is a console.warn.

A related path: refreshIfStale awaits save() inside a try whose empty catch is meant for "offline". If a SecureStore write fails there, the new token exists only in memory, SecureStore keeps the old one, and issuedAt says "fresh". The old token retires 60 s after the new one is used, so the next cold start opens on the login screen.

Evidence
// persist.js (TanStack) — any throw from restoreClient discards the cache
} catch (err) { … await persister.removeClient(); throw err; }
// encrypted-storage.ts:71-78 — any cipher failure, including "key unavailable"
try { stored = SEALED_PREFIX + (await cipher.encrypt(value)); }
catch (error) { events.onPlainFallback?.(key, error); stored = value; }
Why it matters
If the phone starts offline after a Keystore hiccup, the screens come up empty even though the data was on the phone. The plain-text fallback quietly undoes encryption at rest for a while. Both need a Keystore read failure, and how often that happens is unverified.
Recommendation
Wrap the persister. On KeyUnavailableError in restoreClient, return undefined instead of throwing, and skip persistClient until a read succeeds. Limit the plain-text fallback to tt.outbox, the one value worth keeping at any cost, and skip the write for the cache. In refreshIfStale, handle a failed save() on its own: log it and reset issuedAt so the refresh is tried again.

6. Strengths: keep these

  • Fixes that follow the root cause, in layers. CQ-027 was fixed in three places: the schema refuses bad zones, reads heal values already stored, and the job loop isolates each user, catches the tick and logs unhandled rejections. Any one of those layers would have stopped the crash.
  • Commit discipline. All 42 commits are Conventional Commits, each one logical change, with a Refs: CQ-0xx trailer and a body that explains why. None carry co-author or agent lines. d0c9863 explains why sms_imports stays instead of silently ignoring that part of the recommendation.
  • Testable cores pulled out of React Native. session-manager.ts (from auth.ts), phone-writes.ts, widget-pending.ts, server-clock.ts and move-undo.ts follow the outbox-policy pattern: pure rules, injected storage, fast tests.
  • Careful session design. The refresh grace starts only once the new token is used, so a refresh reply lost on the way to the phone signs nobody out. Logout ends both tokens. The legacy branch has a fixed end date and a test that proves it.
  • The assistant boundary got smaller and safer. A handler table with one function per action, ULID-only ids, strict tool schemas with an enum for action, money changes as drafts with the exact request shown to the user, and deletions that always wait for a tap.
  • Migrations that repair before they constrain, with a test that seeds the rows older builds let through. A failed open names the user (as an HMAC tag) in the log.
  • Type hygiene. 0 non-null assertions, 1 justified any, 0 @ts-ignore, strict plus noUncheckedIndexedAccess, and defined() failing loudly with a name.
  • Unchanged strengths. One SQLite file per user, integer money with CHECKs, zod at every boundary, typed RPC, no secrets in git, no barrel files, no file over 800 lines, 0 TODO/FIXME, and backups that check their own integrity, now with an off-site hook.
