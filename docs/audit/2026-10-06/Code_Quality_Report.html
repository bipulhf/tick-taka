1. Executive summary

70 / 100

This is a well-built codebase. The architecture has a clear structure: one SQLite file per user, request scoping through AsyncLocalStorage, zod schemas shared between server and client, and Hono RPC types going all the way to the phone. Lint and typecheck are clean, 185 tests pass, API line coverage is 93.6%, and no source file comes close to the 800-line ceiling.

The serious problems are at the edges. The offline write queue is deleted whenever any request returns 401, and because the 30-day token has no refresh path, that happens on a schedule. Session and token handling are weak: the JWT goes in image URLs and cannot be revoked. A few correctness and operations gaps remain: LIKE search, nightly jobs on the event loop, and no CI. None of these is a deep design flaw, and most can be fixed in under a day.

3.1 Error handling & data integrity

CQ-001 · Any 401 deletes the offline write queue (and the token expires on a schedule)

Critical · Error handling / data integrity · Effort M
Where
apps/mobile/src/lib/http.ts:46-50, apps/mobile/src/lib/auth.ts:103-111, apps/mobile/src/lib/user-data.ts:20-31, apps/api/src/modules/auth/routes.ts:11,43-49, apps/mobile/src/lib/query-client.ts:79
What's wrong
Every response goes through a ky afterResponse hook. A 401 from any non-/auth/ URL calls signOut(), and signOut() runs clearUserData(), which clears the TanStack mutation cache. That cache is the offline outbox. Tokens are issued for a fixed 30 days and the app never refreshes them. So the first write after expiry (a quick-add from the widget or a shortcut, or a write replayed after an offline spell) gets a 401, and the 401 deletes that write along with everything else in the queue. Separately, the persisted cache has maxAge = 14 days, so writes that sat offline longer than that are dropped when the cache is restored.
Evidence
// http.ts:46-50
afterResponse: [({ request, response }) => {
  if (response.status === 401 && !request.url.includes("/auth/")) auth.onUnauthorized();
}],
// auth.ts:111
connectAuth({ token: () => tokenStore.get(), onUnauthorized: () => void signOut() });
// user-data.ts:21-23
await queryClient.cancelQueries();
queryClient.getMutationCache().clear();   // <- queued offline writes gone
// auth/routes.ts:11
export const TOKEN_TTL_SECONDS = 30 * 24 * 60 * 60;   // no refresh endpoint exists
Why it matters
Fast capture that works offline is the product's main promise ("Capture beats organise", offline queue in IMPLEMENTATION_PLAN Phase 7). Losing a logged expense without telling the user breaks trust in the safe-to-spend number.
Recommendation
Separate "session expired" from "sign out". On 401, pause the outbox (onlineManager.setOnline(false) or a paused flag) and send the user to re-authenticate without clearing mutations. Only signOut() started by the user should wipe data, and it should warn first if getMutationCache().getAll().some(m => m.state.isPaused). Add a sliding refresh, for example re-issuing the token on GET /me when it has less than 7 days left. Set the outbox's persisted maxAge to at least the token lifetime.

CQ-002 · Startup hangs on the splash screen if SecureStore or profile parsing throws

High · Error handling · Effort S · Unverified on device
Where
apps/mobile/src/lib/auth.ts:28-35, apps/mobile/src/app/_layout.tsx:66-80
What's wrong
ready requires token !== undefined, and tokenStore starts as undefined. loadToken() is fired with void. If SecureStore.getItemAsync rejects (a known failure after Android Keystore invalidation or a device restore), or if JSON.parse(profile) throws, the store is never set. The layout then returns null forever with the splash screen still showing.
Evidence
// auth.ts:28-35
export async function loadToken(): Promise<void> {
  const [token, profile] = await Promise.all([ SecureStore.getItemAsync(TOKEN_KEY), ... ]);
  profileStore.set(profile ? (JSON.parse(profile) as Profile) : null);
  tokenStore.set(token ?? null);
}
// _layout.tsx
const ready = fontsLoaded && token !== undefined;
useEffect(() => { void loadToken(); ... }, []);
if (!ready) return null;
Why it matters
The app becomes unusable with no message, and the only fix is clearing app data, which also deletes the offline queue.
Recommendation
Wrap the body in try/catch. On failure, delete both keys and set tokenStore.set(null) so the user lands on login. Validate the profile with a small zod schema instead of the as Profile cast.

CQ-003 · No React error boundary anywhere in the app

Medium · Error handling · Effort S
Where
apps/mobile/src/app/ (all route files), especially _layout.tsx
What's wrong
rg -n "ErrorBoundary" apps/mobile/src returns 0 matches. expo-router supports export function ErrorBoundary per route, but none is defined. Any render-time exception, such as an unexpected null in cached data restored from an older build, crashes the whole tree.
Why it matters
Data is cached for 7–14 days and restored on start. If a shape mismatch reaches a render path, the app crashes again on every launch.
Recommendation
Export an ErrorBoundary from _layout.tsx (and from heavy screens such as Insights). Offer "Try again" (retry()) and "Reset cached data" (persister.removeClient(), keeping the outbox). Bump the persister buster whenever API response shapes change.

CQ-004 · Server logging is bare console.*, and the error mapper's branches are untested

Low · Error handling / observability · Effort S
Where
apps/api/src/middleware/error-handler.ts:13-28 (coverage 72%, lines 9, 17, 22-26 uncovered), apps/api/src/jobs/scheduler.ts:27-29, apps/api/src/ai/usage.ts:89, apps/api/src/modules/ai/routes.ts:114
What's wrong
The source has 5 console.* calls in total. Unknown errors are logged with no method, path, user ID or request ID. The HTTPException branch and the SQLite FK/UNIQUE → 400/409 mapping have no tests.
Recommendation
Add a small request-ID middleware and log one JSON line per error, including {reqId, userId, method, path, code}. Add two tests that trigger an FK violation and a duplicate primary key through a route.

3.2 Security

CQ-005 · The 30-day bearer token travels in receipt image URLs

Medium · Security · Effort M
Where
apps/api/src/middleware/auth.ts:15-17, apps/mobile/src/lib/receipts.ts:53-56, deploy/nginx-tick-taka.conf:10-18
What's wrong
Receipt images are loaded from /uploads/<name>?token=<JWT>. Nginx's default combined access log records the full request line. expo-image keys its disk cache by URL. The token is the full API credential, valid for 30 days (see CQ-006).
Evidence
// receipts.ts:54-56
export function receiptUrl(path: string): string {
  return `${apiUrl(`/uploads/${path}`)}?token=${encodeURIComponent(tokenStore.get() ?? "")}`;
}
Why it matters
Anyone who can read server logs, or a backup of them, can act as the user for up to a month.
Recommendation
Pass headers to expo-image instead (source={{ uri, headers: authHeaders() }}), which it supports. If a query parameter is still needed, issue a short-lived signed URL (an HMAC of name+exp, 5 minutes) that is scoped to the one file and cannot be used as an API token.

CQ-006 · Sessions cannot be revoked or refreshed

Medium · Security · Effort M
Where
apps/api/src/modules/auth/routes.ts:43-50, apps/api/src/middleware/auth.ts:19-28, apps/mobile/src/lib/auth.ts:103-109
What's wrong
The HS256 JWT carries only sub/iat/exp, with no jti, token version, aud or iss. Sign-out only deletes the token on the phone, and the server has no record to invalidate. The only kill switch is rotating JWT_SECRET, which signs out every user.
Recommendation
Add token_version INTEGER to users (users.db). Put it in the JWT and compare it in requireAuth (one indexed lookup, which deps.users.find already does). Add POST /auth/logout to bump it. Pair this with the sliding refresh from CQ-001 and shorten the TTL to around 7 days.

CQ-007 · The API binds 0.0.0.0 by default, and the login limiter trusts X-Real-IP

Medium · Security · Effort S
Where
apps/api/src/env.ts:5, apps/api/src/modules/auth/routes.ts:23-29, apps/api/src/middleware/rate-limit.ts:5-27
What's wrong
HOST defaults to "0.0.0.0". Only the README and .env.example say 127.0.0.1. If the port is reachable, clients can set X-Real-IP themselves and get a fresh limiter bucket per request. Requests without the header all share one "local" bucket, so 10 bad attempts lock everyone out. Keys are deleted only on a successful sign-in, so the Map grows by one entry per distinct IP forever. Authenticated and AI routes have no rate limiting at all; only the monthly cost cap applies.
Evidence
HOST: z.string().default("0.0.0.0"),                       // env.ts:5
const ip = c.req.header("x-real-ip") ?? "local";            // auth/routes.ts:27
Recommendation
Default HOST to 127.0.0.1. Trust X-Real-IP only when the socket peer is loopback (Bun: server.requestIP(req)), and fall back to the peer address otherwise. Prune expired keys inside attempt(), or sweep them every N calls. Add a per-user token bucket on /ai/*, for example 30 requests a minute.

CQ-008 · The assistant builds internal request paths from strings chosen by the model

Medium · Security (prompt injection) · Effort S
Where
apps/api/src/modules/ai/assistant/tools.ts:244-251 (also the delete loop around 286-292 and the act paths at 328-382), apps/api/src/modules/ai/assistant/entities.ts:24-25,31, apps/api/src/app.ts:37
What's wrong
id comes from the model's tool arguments (String(args.id)) and is placed straight into `${def.path}/${id}`. status goes into the query string without encoding. app.request() builds a new Request("http://localhost"+path), and URL parsing collapses dot segments. I verified that new URL("http://localhost/tasks/x/../../settings").pathname === "/settings". Text the model reads, such as a transaction note, could therefore steer an "update task" into PATCH /settings, or another route, with the user's own authorization header.
Why it matters
The damage stays inside the user's own database, because per-user isolation holds. It still bypasses the entity allow-list that the tool layer is meant to enforce. The privacy page promises the assistant "can add and change records only through the same checks as the app itself."
Recommendation
Validate every ID with the shared idSchema (ULID regex) before building a path, and reject anything else as a FieldError. Build query strings with URLSearchParams, and check status against the entity's enum.

CQ-010 · All cached financial data and queued writes are stored unencrypted in AsyncStorage

Medium · Security / privacy · Effort M
Where
apps/mobile/src/lib/query-client.ts:74-79, apps/mobile/src/app/_layout.tsx:88-91
What's wrong
The token is stored correctly in SecureStore (auth.ts:96-97). But the whole TanStack cache (accounts, balances, transactions with notes, the assistant chat) and the paused-mutation outbox are written as plain JSON under tt.query-cache. The app lock (features/security/app-lock.tsx) only hides the UI.
Recommendation
Turn off Android auto-backup for the AsyncStorage DB (android.allowBackup=false via a config plugin) at a minimum. For stronger protection, encrypt the persisted blob with a key kept in SecureStore (AES-GCM through expo-crypto), or switch the persister to an encrypted store.

CQ-011 · The code has no account-deletion path, even though sign-up is open and the privacy policy promises deletion

Medium · Security / privacy compliance · Effort M
Where
apps/api/src/modules/site/pages.ts:27,92-95, apps/api/src/db/user-registry.ts:59-64 ("Sign-up is open"), apps/api/src/app.ts:38-66 (no delete route)
What's wrong
The policy says "we delete your account, records, receipt photos and backups within 30 days". No route, script or admin tool does this. An operator would have to find and delete users/<id>.db, its -wal/-shm files, uploads/users/<id>, backups/users/<id> and the users row by hand, while the process still holds the handle open (CQ-013).
Recommendation
Add DELETE /me. It should close and evict the cached handle, remove the DB files, uploads and backups, and delete the registry row. Link to it from Settings. Google Play also requires an in-app deletion path for apps that create accounts.

CQ-009 · Production builds allow cleartext HTTP

Low · Security · Effort S
Where
apps/mobile/app.json:55 ("usesCleartextTraffic": true under expo-build-properties), apps/mobile/src/lib/config.ts:2 (fallback http://10.0.2.2:3000)
What's wrong
The production and preview profiles point at HTTPS (eas.json:12,16), but the APK still allows HTTP to any host. If EXPO_PUBLIC_API_URL is ever missing from a build, it silently falls back to cleartext.

3.3 Performance

CQ-013 · DB handles are never closed, and nightly jobs run synchronously on the only event loop

Medium · Performance / scalability · Effort M
Where
apps/api/src/db/user-registry.ts:87,148-157, apps/api/src/jobs/scheduler.ts:17-37, apps/api/src/jobs/backup.ts:27, apps/api/ecosystem.config.cjs:14
What's wrong
open is a Map that only grows. Every hour, runHourlyJobs calls deps.users.data(user) for every user. That opens (and keeps open) every database, which means 3 file descriptors with WAL plus page cache each, and runs migrations and seeding on first open. At 03:00 local time each user's VACUUM INTO runs synchronously in the same loop that serves requests. Sign-up is open, so this cost grows with every account, and pm2 restarts at 300 MB.
Evidence
for (const user of deps.users.list()) {
  const data = deps.users.data(user);          // opens + caches forever
  runAsUser({ user, data }, () => { ...
    if (hour === BACKUP_HOUR) safely("nightly-backup", () => runBackup(data.sqlite, ...));
Recommendation
Turn the handle cache into an LRU (say 50 entries) that calls sqlite.close() on eviction. Run backups with await and a yield between users (await Bun.sleep(0)), or in a Worker. Skip users whose last_seen_at is older than the newest backup.

CQ-014 · The AI assistant loop keeps spending after the client goes away

Medium · Performance / cost · Effort S
Where
apps/api/src/modules/ai/routes.ts:93-124, apps/api/src/modules/ai/assistant/agent.ts:13-14,165, apps/api/src/ai/openai-client.ts:20, apps/api/src/ai/usage.ts:71-81
What's wrong
The SSE handler never checks stream.aborted or registers stream.onAbort, and no AbortSignal is passed to OpenAI (rg "onAbort|aborted|AbortController" apps/api/src returns 0 matches). A turn can run 12 rounds × 45 s timeout × 1 retry after the phone has given up (client timeout is 90 s). The monthly cap is checked once before the turn starts, so concurrent turns can each overshoot it.
Recommendation
Create an AbortController per request, abort it in stream.onAbort, pass signal into every openai.* call, and check signal.aborted between rounds. Re-check the cap between rounds as well.

CQ-015 · Every mutation invalidates every query

Low · Performance · Effort M
Where
apps/mobile/src/lib/query-client.ts:23-27,41-48
What's wrong
scheduleRefresh() calls queryClient.invalidateQueries() with no filter, 250 ms after any mutation succeeds or fails. Each active screen's queries refetch, which means Today, budgets and insights aggregates are recomputed on the server for a single checkbox tick. The comment ("one user, small data") makes this a deliberate trade-off, but its cost grows with history.
Recommendation
Keep the debounce, but map outbox paths to key prefixes (/transactions → [money, today, insights], /tasks → [tasks, today, plan]). Keep the global invalidate as a fallback for unknown paths.

CQ-016 · /sync/changes is unused, and it and /export return unbounded results

Low · Performance / dead code · Effort S
Where
apps/api/src/modules/sync/routes.ts:11-43, apps/api/src/db/schema/*.ts (only tasks and transactions index updated_at)
What's wrong
The mobile app never calls /sync/changes (rg "sync|changes" apps/mobile/src/lib finds nothing relevant). The endpoint scans 20 tables with updated_at > ?, and 18 of those tables have no index on that column. With since=0 it returns everything in one JSON body. /export also loads every row of every table into memory.

3.4 Data layer

CQ-017 · LIKE search escaping is broken: "50%" and "a_b" never match

Medium · Data layer / correctness · Effort S
Where
apps/api/src/modules/transactions/service.ts:75-76, apps/api/src/modules/tasks/service.ts:155-157
What's wrong
Both services prefix % and _ with a backslash, but SQLite treats a backslash as an escape character only when the query has an ESCAPE '\' clause, and Drizzle's like() does not add one. The pattern then looks for a literal backslash. I verified this with bun:sqlite: '50% off' LIKE '%50\%%' returns 0 rows, and with ESCAPE char(92) it returns 1. The same helper logic is copied in both services.
Evidence
filters.push(like(transactions.note, `%${query.q.replace(/[%_]/g, (m) => `\\${m}`)}%`));
Recommendation
Add a shared helper in apps/api/src/lib/: sql`${col} LIKE ${pattern} ESCAPE '\\'`, and also escape the backslash itself (/[\\%_]/g). Add a test that searches "50%".

CQ-018 · The database has no CHECK constraints, and self-references have no foreign keys

Medium · Data layer · Effort M
Where
apps/api/drizzle/0000_init.sql:151-170 (type text NOT NULL, amount_minor integer NOT NULL), apps/api/src/db/schema/time.ts:34,60 (tasks.parent_id, tasks.goal_id), apps/api/src/db/schema/money.ts:20 (categories.parent_id)
What's wrong
grep -c CHECK drizzle/*.sql returns 0. Drizzle's text(..., { enum }) is enforced in TypeScript only. Enum values, positive amounts for non-adjustments, fee_minor >= 0, month/date formats and ended_at >= started_at all depend on zod alone. Any other write path (the migration in 0002, a future script, a hand fix in sqlite3) can store values the aggregates do not expect. tasks.goal_id was added in 0001 without a reference.
Recommendation
Add check() constraints in the Drizzle schema for enums and signs, and .references() for parentId and goalId. SQLite cannot add constraints in place, so generate a table-rebuild migration and test it against a copy of a real backup.

CQ-019 · Backups stay on the same disk as the live data

Medium · Data layer / operations · Effort M
Where
apps/api/src/jobs/backup.ts:8-11 ("Backups stay on the server"), apps/api/src/env.ts:72-76, README "Backups"
What's wrong
By default BACKUPS_DIR sits next to DB_PATH on the same VPS volume. If the disk fails, the provider deletes the VPS, or someone runs rm -rf ~/tick-taka-data, both the data and all 14 backups are gone. The only off-box copy is the user's manual JSON export.
Recommendation
After VACUUM INTO, push the file to object storage (Backblaze B2 or S3 with rclone from cron, or the S3 client in Bun). Encrypt it with age first, and document a restore drill.

3.5 Architecture, readability & type safety

CQ-020 · A handful of 260–440-line components and closures carry too many responsibilities

Medium · Maintainability · Effort L
Where
features/tasks/task-sheet.tsx:67-509 (TaskSheet, 443 lines), features/money/transaction-sheet.tsx:65-437 (373), api/modules/tasks/service.ts:39-371 (taskService, 333), api/modules/ai/assistant/tools.ts:178-487 (createToolRunner, 310), features/quick-add/use-quick-add.ts:31-297 (267). Full list in Appendix C.
What's wrong
None of these breaks the 800-line ceiling (the largest source file is 509 lines). However, each function mixes several concerns. For example, TaskSheet combines form state, project and area queries, recurrence UI, subtasks, reminders and delete/restore in one render function, and createToolRunner holds find, create, update, delete, a 10-case act switch and the undo log. Split along seams that already exist. Move TaskSheet's recurrence and reminder sections to features/tasks/_components/-style siblings, and move the subtask list to its own component. Move each act case in tools.ts into a table of handlers (Record<Action, (args) => Promise<Result>>) in a sibling module. These are moves, not rewrites. Keep the JSX byte-identical.

CQ-022 · Non-null assertions are allowed, and client JSON is cast without checks

Low · Type safety · Effort M
Where
biome.json:21-24 (noNonNullAssertion: "off"); 44 ! sites in source, e.g. api/modules/ai/planning.ts:53,69 (t.doAt!), api/modules/tasks/service.ts:305,355, api/modules/today/service.ts:119 (debt.remindAt!), mobile/features/plan/day-timeline.tsx:177. Unchecked casts: mobile/src/lib/api.ts:49 (unwrap), api.ts:66 (send<T>), auth.ts:33,86.
What's wrong
Most !s on domain fields rely on a filter defined somewhere else, for example "only tasks with doAt were selected". If that filter changes, the code yields NaN times instead of a compile error. On the client, typed RPC gives compile-time shapes, but persisted cache data from older builds is never re-validated.
Recommendation
Turn the rule back on as warn, and narrow with type guards (.filter((t): t is Task & {doAt: number} => t.doAt !== null)). Validate the few hand-cast client payloads (profile, sign-in body) with zod.

4. Strengths: keep these

  • Isolation by design. Each user has their own SQLite file (user-registry.ts:59-64), and AsyncLocalStorage scoping makes deps.db always point to the current user's database (lib/deps.ts:32-49, lib/user-scope.ts). No query can reach another user's rows, and users.test.ts covers this.
  • Thorough Google ID-token verification. RS256 against JWKS with cache-control TTL, retry on key rotation, iss/aud checks, email_verified required (lib/google.ts).
  • Validation at every server boundary. Shared zod schemas are used through one validate() wrapper with a consistent {error:{code,message,details}} envelope (lib/validate.ts, lib/errors.ts). The env is validated at boot (env.ts, JWT_SECRET at least 32 characters).
  • End-to-end types. The mobile app uses hc<AppType> over ky (mobile/src/lib/api.ts:19), so route and response types come straight from the server.
  • Money done right. Amounts are integer minor units everywhere, conversion happens only at the edges with explicit rounding (shared/src/money.ts), and balances are derived from transactions rather than stored (lib/money-queries.ts).
  • Offline-safe writes on the server. Creates are idempotent on client ULIDs, last write wins against the server clock (x-server-time), multi-row writes run in transactions, and upserts correctly revive soft-deleted rows under unique indexes (budgets/service.ts:216-248, category-rules/service.ts:17-30).
  • AI guardrails. A per-feature off switch, a monthly cost cap, a fake provider in tests, and assistant writes that go through the app's own validated routes with undo records.
  • Hygiene. 0 lint diagnostics, 0 type errors, 185 passing tests, API line coverage 93.6%. One any (and that one is commented), no @ts-ignore, no TODO/FIXME, no runtime import cycles, no barrel files, largest source file 509 lines. No secrets in git history. Public HTML pages escape their inputs. Upload file names are regex-checked (no path traversal).
  • Secure token at rest. The JWT is kept in expo-secure-store, and sign-out wipes cache, queue, notifications and widget data.
