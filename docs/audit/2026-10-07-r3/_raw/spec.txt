  Positioning
  Tick & Taka is a private, single-user mobile app that runs my days and my money from one
  screen. "Tick" is time, "Taka" is money; the name is a working title.

  The problem. Time apps and money apps live apart, so neither knows what the other sees.
  Logging in both feels like a chore, so both get abandoned within weeks.

  The promise. Open the app and see today: what to do next, and how much I can safely
  spend. Log anything in under five seconds.

  Who it is for. One person juggling several workstreams at once: two remote jobs, teaching,
  research and home. There are no other users, so there is no sharing, onboarding or team
  features.

  Platform: Android only. The app is built, tested and installed as an APK for Android alone,
  with no iOS version. That frees it to use Android-only features without workarounds:
  reading SMS, home-screen widgets, long-press app shortcuts ("Add expense", "Start
  focus"), and action buttons on notifications.

  Guiding principles

        Capture first, organise later. Any task, expense or time entry takes one tap plus
        typing. Sorting happens in the evening review, not at capture.
        Today over everything. The home screen answers two questions: "what now?" and
        "can I afford it?"
        Reward, never guilt. Progress gets a small celebration. A missed day gets a shrug,
        never a red warning.
        Honest numbers. Account balances and tracked hours always reconcile. No rounded
        or estimated totals presented as facts.
        Every feature earns its place. A feature I don't touch for a month gets hidden or
        removed.
        My data, my server. Everything lives on my own VPS and exports to a single file
        anytime.

  What it is not: a bank-sync aggregator, a team tool, or a full calendar replacement.

  Design language
  The app should feel like a cheerful pocket companion: soft shapes, warm colours, bouncy
  feedback, and zero guilt. Playfulness is there to make logging feel rewarding, so it must
  never slow a task down.

  Mascot: Tiki. A round coin with a little clock face. Tiki reacts to the day: proud when the
  top three tasks are done, relaxed when spending is under budget, sleepy after 11 pm.
  When I overspend, Tiki looks calm and offers a tip, never sad or angry. Start with 6–8 SVG
  expressions swapped with Reanimated; move to Rive animations only if it feels flat.

  Time features lean blue, money features lean green and coral, so I always know which half
  of the app I'm in at a glance.

  Typography. Nunito for all UI text: rounded, friendly and very legible. Every amount and
  timer uses tabular digits ( fontVariant: ['tabular-nums'] ) so numbers don't jiggle
  while they animate. Add Hind Siliguri later if I want Bangla labels. Amounts always show
  the ৳ sign.

  Motion and feel

        Springs, not linear easing, for every transition (Reanimated).
        Ticking a task: the checkbox pops, a light haptic fires, a spark flies to the score.
        Big wins only get confetti: all top three done, a savings goal reached, a 30-day streak.
        Rarity keeps it special.

        Balances and totals count up to their new value instead of jumping.
        Respect the phone's "reduce motion" setting.

  Light gamification. Sparks are points earned by finishing tasks, completing focus
  sessions and logging expenses on the day they happen. Sparks raise a level that unlocks
  cosmetic rewards only: themes, Tiki outfits, app icons. Habit and logging streaks get 2
  freeze days per month, so one bad day never breaks a long run. No leaderboards, no
  penalties.

  Interaction rules

        Primary actions sit in the bottom half of the screen, inside thumb reach.
        Tap targets are at least 48 dp.
        Swipe right to complete or check off; swipe left to snooze or edit.
        Creating and editing happen in bottom sheets, never on a new full screen.
        Deleting shows an Undo snackbar instead of an "Are you sure?" dialog.
        Every empty state shows Tiki plus exactly one suggested action.
        Copy is short and friendly: "Safe to spend today: ৳640", not "Remaining daily
        discretionary budget".
        Dark mode follows the system setting.

  Today screen, top to bottom

   1. Greeting, date and Tiki's mood for the day.
   2. Safe-to-spend card: how much I can spend today without breaking this month's
        budgets, plus what I've spent so far today.
   3. Top three: the three tasks I picked for today, with big checkboxes.
   4. Timeline: time blocks, tasks with a time, and bills due today on one vertical line, topped
        by a "does my day fit?" bar.
   5. Habits row: round chips I tap to check off.
   6. Running timer: a sticky bar while a focus session or time entry is running.
   7. This Evening: after-work tasks, kept apart from the working day, followed by the next

  SMS auto-capture
  The app reads bank and mobile-wallet SMS on my phone and turns each transaction
  message into a ready-made card in an SMS review panel. Nothing is saved until I tap Add,
  so a wrong parse never pollutes my numbers.

  How a message becomes a transaction

   1. Permission, once. On first use, an explainer screen asks for READ_SMS and
      RECEIVE_SMS .
   2. Only allowed senders. In Settings › SMS sources I pick which sender IDs count (bKash,
      Nagad, my banks) and map each to an account. Every other message is ignored, as is
        anything containing "OTP", "code" or "PIN".
   3. Scan. Each time the app opens, it reads allowed messages that arrived since the last
      scan. A background receiver also catches new SMS while the app is closed.
   4. Parse on the phone. A template per sender pulls out amount, direction, fee, balance
      after, transaction ID and the other party. Templates are built from 2–3 of my own real
      messages per sender, pasted in during setup.
   5. AI fallback. A message no template matches goes to /ai/parse with account
        numbers, phone numbers and names masked. The reply is a draft like any other.
   6. No duplicates. Each message is fingerprinted by its transaction ID, or by sender + time
      + amount when there is no ID. A fingerprint is never offered twice.
   7. Learn from edits. If I change a card's category, the rule is saved to category_rules , so
        the same merchant comes pre-filled next time.

  What has to change in the build

        Expo Go can't load custom native code, so the app moves to a development build
        ( expo-dev-client ) built with EAS.
        A small local Expo module, sms-reader , written in Kotlin, provides two things:
        getMessagesSince(timestamp, senders) reading content://sms/inbox , and an
         onSmsReceived event from a broadcast receiver.
         app.json declares the READ_SMS and RECEIVE_SMS Android permissions.
        The app stays a sideloaded APK. Google Play only allows SMS permissions for default
        SMS apps, so it never goes to the Play Store, which suits a single-user app anyway.

  Data and API

        New table sms_imports : fingerprint, sender, received_at, parsed amount and
        direction, status (pending, added, ignored) and transaction_id.
         POST /sms-imports sends a batch of parsed cards and returns which fingerprints the
        server already knows, so reinstalling the app never re-offers old messages.
         PATCH /sms-imports/:fingerprint records Add or Ignore.
        Raw SMS text never leaves the phone, except the masked text in an AI fallback. The
        server stores parsed fields and the fingerprint only.

  How it runs

        All AI calls go through the backend under /ai/* . The OpenAI API key lives only in the
        server's environment variables, never in the app.
        The backend uses the official openai npm package, which runs on Bun.
        Parsing features use Structured Outputs with a JSON schema built from the same Zod
        schemas the API already validates with, so replies always fit the database shape.




                                                                                                               Page 17 of 37
Tick & Taka — Product & Technical Spec




        "Ask my data" uses function calling. The model can only pick from functions such as
         spendByCategory(from, to) or hoursByArea(from, to) . It never writes or runs SQL.
        Model names live in environment variables (a small, cheap model for parsing and
        categorising; a stronger one for the weekly coach), so I can switch models without a
        code change.

  Guardrails

        Rules first. Obvious inputs like "lunch 250" are parsed on the phone and never hit the
        API. Repeated notes reuse the last category without an AI call.
        Cost cap. Every call's token usage is logged in an ai_usage table. AI switches off for
        the rest of the month once a cap I set in Settings is reached.
        Graceful fallback. Offline, over the cap, or on an API error, the app falls back to the
        plain form with nothing lost.
        Minimum data. Requests carry only the fields a feature needs. Account numbers are
        never sent, and names in debts are replaced with placeholders.
        Off switch. One toggle in Settings disables all AI features.

  This is the one place data leaves my server, so it is a deliberate exception to the "my data,
  my server" principle and stays opt-in per feature.

  API design
  A plain JSON REST API in Hono, with Hono's typed RPC client ( hc ) on the phone so every
  call is type-checked end to end without writing a client by hand.

  Auth for one user

        No users table. The server holds one password hash ( APP_PASSWORD_HASH ) in its
        environment, made with Bun.password.hash .
         POST /auth/login checks the password and returns a JWT signed with JWT_SECRET ,
        valid for 30 days (Hono's hono/jwt middleware).
        The app stores the token in expo-secure-store and sends it as Authorization:
        Bearer <token> on every request.
        Login is limited to 5 attempts per 15 minutes per IP, read from the X-Real-IP header
        Nginx sets.
        Every body and query is validated with Zod through @hono/zod-validator . Errors
        always return { "error": { "code", "message" } } .

  Notifications, offline, backup and security
  Notifications are scheduled on the phone, not pushed from the server. After each sync
  the app re-schedules them with expo-notifications , so there's no push service to run.


     Notification                   When

     Task reminder                  At the task's reminder time

     Bill due                       2 days before, and at 9 am on the due day

     Habit nudge                    At the habit's chosen time, only if it isn't checked
                                    yet

     Focus timer                    When a work or break period ends

     Daily shutdown                 9:30 pm

     Weekly review                  Sunday evening


  Quiet hours run from 11 pm to 7 am; anything scheduled then waits until morning.

  Server jobs. One small scheduler (the croner package, set to Asia/Dhaka) runs inside
  the same Bun process: marking bills overdue just after midnight and taking the nightly
  backup. A repeating task creates its next copy when the current one is completed, so no
  job is needed for that.

  Offline behaviour

        TanStack Query keeps a persisted cache on the phone, so every screen opens instantly
        and still works without internet.
        Changes made offline are queued and sent in order when the connection returns.
        Because IDs are generated on the phone, offline-created records never clash with
        server records.
        Conflicts resolve by last write wins on updated_at , which is safe with a single user.

  Backups

        Every night at 3 am the server runs VACUUM INTO to write a clean copy of the database
        to a backups folder next to it, keeping the last 14 days.
        Backups stay on the server; nothing is uploaded to any outside storage.



                                                                                           Page 25 of 37
Tick & Taka — Product & Technical Spec




        Settings has an Export button that downloads the full JSON export to the phone. It is
        the only copy that lives outside the server, so it's worth tapping now and then.
        Once a month, restore a backup to a local copy to confirm it actually works.
        Keep the backups folder on a different disk or partition from the live database if the
        VPS has one.

  Security

        HTTPS only, through Nginx with a Let's Encrypt certificate from Certbot (renews
        automatically). The Bun process listens on 127.0.0.1, so only Nginx can reach it.
        App lock with fingerprint or face ( expo-local-authentication ) after 5 minutes in the
        background.
        Privacy mode: one tap blurs all amounts on screen, handy when using the app in public.
        Receipt images are stored in an uploads folder next to the database and served only to
        authenticated requests.
        Secrets ( APP_PASSWORD_HASH , JWT_SECRET , OPENAI_API_KEY ) live in a .env file on the
        server with permissions set to 600, never in Git.
        The SQLite file sits in a data folder outside the repository and is never served over
        HTTP.
