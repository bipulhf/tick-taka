8.1 Data trust and recovery

UX-052 · The export offered before deleting an account is deleted when the share sheet returns, and nothing confirms it was saved

Medium User control / feedback · New (side effect of d1a610c) · code path verified, share-target behaviour Unverified · Effort S-M
Where
features/settings/use-export-data.ts:90-112; features/settings/delete-account.tsx:42-55; lib/export-file.ts; lib/user-data.ts:18-25, 40 (sweep on sign-out); node_modules/expo-sharing/android/.../SharingModule.kt:52, 80-82 (resolves in onActivityResult)
What's wrong
exportData writes the full JSON to the cache folder, awaits Sharing.shareAsync, and deletes the file in finally. On Android, expo-sharing resolves when the chooser's activity result comes back. That isn't proof the receiving app has finished reading the content:// URI. Gmail sends in the background after the compose screen closes, and Drive queues an upload after "Save". If they read the file after it is gone, the save fails inside the other app, where Tick & Taka can't see it. On top of that, a successful export shows nothing at all, and step "1. Keep a copy" on the Delete-account page has no done state. The user moves on to typing DELETE with no sign that a copy exists.
Evidence
const data = await send("GET", "/export");
file = new File(Paths.cache, exportFileName(new Date()));
file.write(JSON.stringify(data));
await Sharing.shareAsync(file.uri, { mimeType: "application/json", ... });
} catch (error) { notify(friendlyError(error)); }
finally {
  // The share sheet has its copy; ...
  if (file?.exists) file.delete();      // right after the chooser returns
  setBusy(false);                       // no success message anywhere
}
Why it matters
The export is the only copy of the data outside the server. The Delete-account page offers it as the step before the one irreversible action. A copy that silently failed, followed by a confirmed deletion, is permanent data loss. The privacy reason for deleting the file is sound, but a sweep on sign-out (and so on account deletion) already exists.
Recommendation
  1. Don't delete in finally. Sweep export files older than an hour when the app starts, and keep the sign-out sweep.
  2. Better still, offer "Save to…" through the Storage Access Framework (expo-file-system's directory picker), so the app knows when the write has finished. Then say "Saved tick-taka-export-2026-10-07.json".
  3. Show a done state under step 1 ("Copy made · 14:02"). If no copy was made in this visit, word the confirm button's caption accordingly.
  4. Check on a device with Drive, Gmail and Files.

10. Three bigger redesign suggestions

R1. Labels first on the widget, measured, not estimated (UX-049, UX-055)

Size classes are now a tested function, which is the right base. The next step is a priority order inside each size: names for Task and Expense first, then one quick-log, then the second quick-log, then glyphs as a last resort. The widths should come from real padding, not an allowance. Two further inputs belong in the cache: whether the assistant is available, and the system font scale (from PixelRatio.getFontScale() when the app writes the cache), so that labels are measured at the size they will be drawn. One test per size class should assert what a sighted user reads.

R2. Colour roles for controls, enforced like grape and mango (UX-050, UX-051)

The colour test proved itself on grape and mango. Give each semantic colour an allow-list (mint and coral only in money and budget code, sky for time) and a second rule: bright tokens may not be the only cue in a list or grid cell. Add one "control colours" line to DESIGN.md (buttons: primary, secondary, time, ghost; switches: ink), and let ToggleRow and Button be the only way to draw them. That turns the remaining residue into compile or test failures.

R3. Make the trust moments explicit (UX-052, UX-054, UX-056)

Three places tell the user something about their data without proof: the export ("did it save?"), a refused write ("saved on this phone"), and the time zone ("whose today is this?"). Treat each as a small status the app owns. The export records when a copy was made and shows it on the Data and Delete pages. Failure copy comes from what the outbox actually did (kept, set aside or dropped), not from the error's shape. The time zone is shown where planning settings live and flagged when the phone disagrees.
