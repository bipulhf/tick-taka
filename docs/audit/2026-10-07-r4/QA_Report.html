5.1 Offline sync

QA-401 · A stuck edit of an account, category, area or budget line takes every later write that uses that record aside with it, and Discard drops them all

Medium Category: Offline / data loss Effort: S–M Reproduced

Where: apps/mobile/src/lib/outbox-policy.ts:L110-L136 (writtenIds takes every record id in the path; mentionsAny matches any id anywhere in the body). outbox-queue.ts:L424-L443 (park), :L266-L271 and :L446-L456 (a new write joins a group), :L138-L146 (discardStuck drops the whole group). components/ui/sync-status.tsx:L19-L26, L55-L58, L72-L78 (card and Discard). The labels used as the description: money/account-sheet.tsx:L62-L66, settings/category-sheet.tsx:L73, plan/area-sheet.tsx:L61 (“Couldn't save”).

What's wrong: The QA-301 fix sets aside “every later write that names a record it creates or edits”. For a stuck create that's right. For a stuck edit of a record that already exists, it isn't. PATCH /accounts/A (rename), POST /accounts/A/balance-check, PATCH /categories/C, PATCH /areas/X and PUT /budgets/2026-10/C (Tiki's budget draft) all put an existing record's id in the path. After that, any expense with accountId: A or categoryId: C, and any task with areaId: X, joins the stuck group, even though it would land without trouble. Every write queued later also joins at once, and its promise rejects with SetAsideError, while the screen has already shown it as saved. The card describes the group by the head's label, which is failure text. So it reads “Couldn't save, and 2 later changes to it”. One Discard then removes the account edit and every expense in the group. Only an 8-second snackbar Undo protects them.

// Real OutboxQueue; PATCH /accounts/A answers 500 every time, everything else works.
OVERGROUP: stuck = ["PATCH /accounts/01M4…","POST /transactions","POST /transactions"]
           | T2 promise: SetAsideError | expenses on server: 0
OVERGROUP: Discard on the account edit dropped 3 writes | expenses on server: 0 | queue size 0
BUDGET-GROUP: stuck = ["PUT /budgets/2026-10/01M4…","POST /transactions"] | expense on server: false

Why it matters: The trigger is uncommon: one edit has to fail 8 times with a non-503 5xx. When it happens, though, the result works against the product's core numbers. Expenses the user logged aren't on the server. So after the next refetch they disappear from Today's safe-to-spend, and one tap on Discard, made to drop a failed rename, deletes them for good. The outbox tests only check writes that depend on a stuck create (outbox-queue.test.ts:L327-L400). Nothing checks that unrelated users of an edited record keep going.

Recommendation: Only a create passes its dependency on to writes that mention it in the body. For an edit, a delete or an action, group only later writes whose path targets the same record. Describe the group by kind (“Edit account bKash · 2 expenses waiting with it”), not by the failure label. Before discarding a group that contains creates, name them in the snackbar.

const created = new Set(createdIds(entry.request));   // POST body.id / transactionId
const targets = new Set(pathIds(entry.request));       // record an edit/delete/action acts on
const dependsOn = (later: OutboxRequest) =>
  mentionsAny(later, created) || pathIds(later).some((id) => targets.has(id) || created.has(id));

5.2 Privacy & data portability

QA-402 · The export file is deleted as soon as the share promise resolves, which may be before the chosen app has read it

Medium Category: Data portability / account deletion Effort: S Unverified on device

Where: apps/mobile/src/features/settings/use-export-data.ts:L16-L34. features/settings/delete-account.tsx:L41-L53 (“1. Keep a copy … Save it before you go on”). node_modules/expo-sharing/android/src/main/java/expo/modules/sharing/SharingModule.kt:L39-L52, L80-L83 (the chooser is started for result, and the promise resolves on any activity result).

What's wrong: The QA-307 fix deletes the file in finally, right after await Sharing.shareAsync(file.uri). On Android that promise resolves when the chooser returns an activity result. Some targets return it as soon as they open, especially ones started in their own task. Others return it when their own screen closes, then upload or attach the file afterwards from the content:// URI (Drive's background upload, a mail draft sent later). In both cases the file may already be gone when the target reads it. The upload fails, or the attachment is empty, and the app has already shown nothing went wrong.

const data = await send("GET", "/export");
file = new File(Paths.cache, exportFileName(new Date()));
file.write(JSON.stringify(data));
await Sharing.shareAsync(file.uri, { mimeType: "application/json", … });
} finally {
  if (file?.exists) file.delete();   // runs as soon as the chooser reports back

Why it matters: The export is the user's only copy of their data outside the server. The delete-account page asks for it as step 1, just before an irreversible delete. If the share silently failed, the user deletes the account believing they have a backup. Round 3's recommendation (“Delete the file once shareAsync resolves”) didn't account for this. This report corrects it.

Recommendation: Don't delete right after the share. Sweep exports older than about an hour at the next app start, and on sign-out (already done). Better: save through the Storage Access Framework (Directory.pickDirectoryAsync() in expo-file-system), so the app writes the file to a folder the user picks, knows it was written, and can say “Saved to Downloads/tick-taka-export-2026-10-07.json”. Then delete-account can show that confirmation. Test on a device with Drive, Gmail and Files as targets.

5.3 Money & Undo

QA-403 · Undo of a Skip that changed nothing moves the bill back, while that period's payment stays logged

Low Category: Money / Undo Effort: S Reproduced

Where: apps/api/src/modules/recurring/service.ts:L71-L78 (movedOnceFrom infers the move from dates), :L133-L134 (a late pay or skip changes nothing), :L201-L206 (unpay: “A skip logs nothing, so only the date says whether it went through”).

What's wrong: A skip leaves no record. So unpay {skip:true} moves the bill back whenever its date is one step past dueAt, whoever moved it there. Here is how that happens. The user taps Paid on Today (offline, or while the recurring sheet is still cached). They then open the bill's sheet, which still shows 5 Oct, tap Skip, and then Undo. The Skip did nothing, because the bill had already moved. But its Undo moves the bill back to 5 Oct, and October's expense stays logged.

STALE-SKIP-UNDO: skip reply moved=false | unpay movedBack=true nextDueAt=2026-10-05
                 | October expenses still logged=1

Why it matters: The bill shows as due, then overdue, for a period that is already paid, which invites a second payment. The trigger is narrow, since it needs a stale screen and an Undo.

Recommendation: Record who moved the bill. Store the pay's or skip's transactionId on the recurring row when it advances (for example moved_by), and have unpay move it back only when moved_by === input.transactionId. This replaces the date inference for both pay and skip. Add the test from section 8.

QA-404 · A bill paid from a Tiki draft has no Undo, although the draft holds everything /unpay needs

Low Category: AI / Undo Effort: S

Where: apps/api/src/modules/ai/assistant/actions.ts:L92-L120 (pay_bill proposes and records with no undo). apps/mobile/src/features/assistant/use-assistant.ts:L220-L240 (Save records undo: draft.undo, which is undefined here). apps/api/src/modules/transactions/service.ts (deleting the expense doesn't touch the bill). README.md (“money actions … are corrected in their own screens”).

What's wrong: The app always asks for drafts (draftMoney: true), so “pay my internet bill” becomes a pay draft with transactionId and dueAt. After Save, the chat shows “Saved: Pay Internet” with no Undo. The README's suggested fix, deleting the expense in Money, leaves the bill a month ahead. That is the same symptom QA-303 fixed for Today. Contributions to goals and debt repayments in the chat also have no Undo, but their reversal isn't a single write.

Why it matters: Today's Paid can be undone, but the same pay from Tiki can't. The user has to know to edit the due date by hand. This goes against the app's own rule, “Undo instead of ‘Are you sure?’, as everywhere else in the app” (sync-status.tsx:L73).

Recommendation: In pay_bill, add undo: { method: "POST", path: `${billPath}/unpay`, body: { transactionId, dueAt, skip: Boolean(raw.skip) } } to both the draft and the direct action, and update the README line.

5.4 Widget

QA-405 · An Undo on the widget is lost if the app picked up the log while its storage key couldn't be read

Low Category: Widget / offline Effort: S Unverified on device

Where: apps/mobile/src/features/widget/widget-pending.ts:L32-L46 (logs are queued, then kept on the widget when durable() is false). widget-task-handler.tsx:L64-L66 (Undo only removes the log from the widget's list). lib/outbox-queue.ts:L209-L216, L499-L511 (while the saved queue can't be read, writes wait on the side key and are sent once it can be read).

What's wrong: When the outbox can't read its saved queue (a Keystore hiccup), the hand-over still queues each widget log. The log goes to the outbox's side key, saved in plain text by the fallback. The widget keeps its own copy, which is correct for durability. If the user then taps Undo on the widget within its 10-minute window, undoQuickLog finds the log in the widget's list, removes it from there, and queues no delete. The outbox's copy is still on the side key. It is sent once the key reads again, and the expense the user took back is saved.

Why it matters: Today's spending is too high by the amount taken back, and nothing on screen says why. It needs a Keystore failure and a widget Undo, so it is rare.

Recommendation: When undoQuickLog removes a log from the waiting list, also add its id to the pending deletes. A DELETE for an id the server never saw answers 404, which the outbox already treats as done (outbox-policy.ts:L70-L73). If the outbox did send the create, the delete follows it in order.

  • The outbox is honest about storage. Writes are on disk from the first tap. A failed save is reported once and shown until a save works. The widget keeps its own copy until the outbox is durable. A sealed queue that can't be read is never written over.
  • Defensive time handling. A missing x-server-time is NaN, not 1970. A saved offset that puts “now” before 2024 is ignored, and the server treats a pre-2024 stamp as unstamped. Every screen uses the user's zone, and a test enforces it.
  • Narrow assistant powers. Settings are allow-listed with an Undo, and budget drafts touch one line. A refused key refuses the whole call, so a mixed request can't sneak a risky key through.
  • Failure-shape awareness. The error-envelope check tells proxy pages apart from API refusals. A 413 is dropped instead of retried forever. The cache buster is versioned, with a comment that says when to bump it.
  • Clean gates. Biome, typecheck, 774 tests and the audit allow-list all pass in CI, and the README explains the coverage limits.

Appendix C — Requirement checklist used

From PRODUCT.md and the spec: log anything in under 5 s. Today answers “what now?” and “can I afford it?”. Safe to spend = flexible left ÷ days left including today, with fixed bills excluded. Amounts are integer minor units. Offline cache with queued writes sent in order, ids made on the phone, last-write-wins on updated_at. Asia/Dhaka by default for display, with local strings for habit dates and budget months. Streaks with 2 freezes a month. Reward, never guilt. Honest numbers (balances and hours reconcile). AI: rules first, a cost cap, graceful fallback, minimum data, an off switch, and never saving money without confirmation. App lock after 5 min. Receipts served only to authenticated requests. Login limited to 5 per 15 min. Bun listens on 127.0.0.1. Nightly VACUUM INTO backup keeping 14. JSON export. Local notifications with quiet hours 23:00–07:00. Bangla and English quick-add.

The fix contracts from rounds 1 to 3 add: revocable sliding sessions with a 60 s grace for a refreshed-away token. A 401 never clears the queue, and signing out with pending writes asks first. Zone validation and per-user job isolation. CHECK→400. Stuck-write parking with Retry and Discard. Money drafts for budgets and amount fields. A persisted clock offset. Round 3 adds: dependent writes grouped with a stuck one, one-line budget writes, an Undo of a pay that survives a lost reply, writes durable before the outbox loads, no cache loss on a key failure, assistant settings limited with an Undo, export clean-up, and zone-aware today/month on every screen.
